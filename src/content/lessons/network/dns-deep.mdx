[What happens when you press Enter](/learn/web/request-journey/) treated DNS as one step: name in, address out (or exit 6). Inside that step is a small treasure hunt, and a cache that decides how fast any change you make reaches everyone else.

## The walk

Your laptop doesn't know where `shop.bamboo.example` lives, and neither does any single server on the internet. DNS is a tree, and each level only knows who's in charge of the level below (RFC 1034):

The **TTL** is "the time interval (in seconds) that the resource record may be cached" (RFC 1035). It makes DNS fast: a popular name is looked up once, then answered from memory thousands of times. It also makes DNS slow to change. When you edit a record, you change only the zone's server. Every cache that already holds the old answer keeps using it until its copy expires, and you can't reach out and clear other people's caches.

## Move a site

The shop is moving from `203.0.113.10` to `203.0.113.20`, and the record has a one-hour TTL. Your job is to switch off the old server without a single visitor being sent to it. The resolver here stands in for the thousands out there, each of which filled its cache at a different moment.

<Callout kind="trap">
Lowering the TTL *and* moving at the same moment doesn't help. Caches that fetched the record before you lowered it still hold the old one-hour TTL. Lower it first, wait out the **old** TTL, then move, and keep the old server running for one **new** TTL after that.
</Callout>

<Callout kind="real">
Inside Kubernetes, a pod's `/etc/resolv.conf` lists search domains such as `<namespace>.svc.cluster.local` and sets `options ndots:5`. A name with fewer dots than `ndots` is tried with each search domain first (resolv.conf(5)). So a pod looking up `api.example.com` (two dots) first asks for `api.example.com.<namespace>.svc.cluster.local` and the other search domains, and gets NXDOMAIN for each, before trying the real name. Writing the name with a trailing dot, `api.example.com.`, skips the search list.
</Callout>

<DoItForReal id="net-dns-real">

`dig` shows the TTL counting down in a real cache, and `+trace` does the root-to-zone walk itself:

```bash
dig example.com A +noall +answer          # note the TTL column
sleep 10; dig example.com A +noall +answer   # same answer, TTL about 10 lower: cached
dig example.com A +trace                  # root -> .com -> the zone's own servers
```

With the tilt platform up, look at the search list a pod really gets:

```bash
kubectl run dnsprobe --rm -it --image=busybox:1.36 --restart=Never -- cat /etc/resolv.conf
```
