An IPv4 address like `10.244.1.37` looks like four numbers. It's really one 32-bit number, written a byte at a time so people can read it (RFC 791). Each of the four parts is 8 bits, so each runs from 0 to 255. That's why `10.244.1.256` isn't an address.

Routers don't look at addresses one by one. They look at **prefixes**: the first few bits, which say which network an address belongs to. CIDR notation writes the prefix length after a slash (RFC 4632):

- `10.244.1.0/24` means "every address whose first 24 bits match `10.244.1`". The last 8 bits are free, so that's 256 addresses.
- `10.244.0.0/16` fixes 16 bits and frees 16: 65,536 addresses.
- `/32` is exactly one address. `/0` is all of them.

Each bit you take off the prefix **doubles** the block. A /23 is two /24s side by side, which is why `10.244.0.0/23` covers both `10.244.0.x` and `10.244.1.x`.

## Read the bits

Type any address with a prefix. The blue bits are the network part, the grey bits are free for hosts. Try `10.244.1.37/24`, then change only the prefix to `/23` and `/25` and watch the range grow and shrink.

<Callout kind="trap">
"Usable hosts" is two fewer than the block size. The first address names the network itself and the last is the broadcast address, so a /24 has 254 hosts, not 256. Point-to-point links are the exception: a /31 uses both of its addresses (RFC 3021).
</Callout>

## Private, public and the odd ones

Three ranges are set aside for private networks. They're never routed on the public internet, so every home, office and cluster can reuse them (RFC 1918):

| Range | Size | Where you'll see it |
|---|---|---|
| `10.0.0.0/8` | 16.7 million | clusters, corporate networks, kind's pods |
| `172.16.0.0/12` | 1 million | container and cloud networks - and the one people misremember |
| `192.168.0.0/16` | 65,536 | most home routers |

The middle one catches people out: `/12` covers `172.16.x.x` to `172.31.x.x` only. `172.32.0.1` is a public address.

A few more show up often enough to recognise on sight (RFC 6890 keeps the full list). `127.0.0.0/8` is loopback, this machine talking to itself. `169.254.0.0/16` is link-local, which usually means "no DHCP server answered", though cloud providers also put their metadata service at `169.254.169.254`. `100.64.0.0/10` is shared address space used for carrier-grade NAT.

<Callout kind="real">
Real clusters vary. kind gives pods `10.244.0.0/16` and Services `10.96.0.0/16`. The controller manager hands each node a /24 of the pod range by default (`--node-cidr-mask-size`). Cloud clusters often give pods addresses straight from the VPC instead. Check yours before you write a rule that relies on it.
</Callout>

<DoItForReal id="net-subnets-real">

With the tilt platform up, read the real slices off your own cluster:

```bash
kubectl get nodes -o custom-columns=NODE:.metadata.name,PODCIDR:.spec.podCIDR
kubectl get pods -A -o wide | head -20      # the IP column: which node's slice?
kubectl get svc -A | head -10               # Service addresses: a different range
```

Each pod's address falls inside its node's `podCIDR`, and every Service address sits outside the pod range entirely.
