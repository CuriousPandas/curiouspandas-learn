An address gets a packet to a machine. A **port** gets it to one program on that machine. A port is a 16-bit number, 0 to 65535. A web server usually listens on 443, a Postgres database on 5432, and the app you just wrote on whatever you told it.

A program that wants connections opens a **listening socket**: an address, a port, and a promise to answer. Two details decide who can reach it:

- **The port.** Connect to 8081 when the program listens on 8080 and you reach nobody.
- **The address it listens on.** `0.0.0.0` means every address this machine has. `127.0.0.1` means loopback only, so only programs on the same machine can connect. Many development servers default to `127.0.0.1`, deliberately, so a half-finished app isn't exposed to the whole network.

## Three packets

TCP opens a connection with a three-way handshake (RFC 9293). The client sends **SYN** ("let's talk"). The server replies **SYN, ACK** ("yes, and let's talk"), and the client sends **ACK**. Only then does any real data flow.

How the handshake *fails* is the useful part, because each failure has its own shape:

When the SYN gets no answer, the client sends it again. Classic TCP waits one second and doubles each wait after that (RFC 6298), and that is the schedule the simulator above shows. Since Linux 6.5 the first few retries are one second apart and only then start doubling (`tcp_syn_linear_timeouts`, default 4). Either way, with the default `tcp_syn_retries` an attempt to a silent address takes about two minutes to fail (131 seconds on current kernels). That's why a dropped connection without a `--connect-timeout` can hang for two minutes.

## Works on my machine

The app runs, and `ss -tln` on the server shows it listening. A teammate on another machine still gets "Could not connect to server". Find out why, and fix it properly.

<TcpLab mission="net-works-on-my-machine" />

<Callout kind="trap">
"Connection refused" doesn't always mean the program is down. A firewall REJECT rule answers SYNs with an ICMP "port unreachable" by default (iptables `--reject-with`), and the client reports that as refused too. Look at *which* machine answered before you restart the app.
</Callout>

<Callout kind="tip">
Exact timings depend on the operating system. On Linux a refusal comes back in about one round trip. On Windows, curl 8.19 took **2,014 ms** to report a refused connection to `127.0.0.1` port 9, because Windows retries a refused SYN before giving up (measured for this lesson on Windows 11). A dropped SYN with `--connect-timeout 3` took 3,007 ms. Fast and slow are still clearly apart.
</Callout>

<Callout kind="real">
The same bug shows up in containers. A process listening on `127.0.0.1` inside a container can't be reached through a published port or a Kubernetes Service, because that traffic arrives on the container's own network interface, not on loopback. The usual fix is configuration, such as a `--host 0.0.0.0` flag or a `HOST` variable, not networking.
</Callout>

<DoItForReal id="net-tcp-real">

On any Linux machine or WSL, watch the three outcomes for real:

```bash
python3 -m http.server 8080 --bind 127.0.0.1 &   # listening on loopback only
ss -tln | grep 8080                               # LISTEN 127.0.0.1:8080
curl -sS http://127.0.0.1:8080/ -o /dev/null; echo "exit $?"    # 0
curl -sS http://127.0.0.1:8081/; echo "exit $?"                 # 7, instant
curl -sS --connect-timeout 3 http://10.255.255.1:8080/; echo "exit $?"   # 28, after 3 s
kill %1
```

`10.255.255.1` is a private address that nothing on most networks answers, so it stands in for a dropped packet.
