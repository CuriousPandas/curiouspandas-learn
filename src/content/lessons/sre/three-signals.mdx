[The dashboard that lies](/learn/platform/observability/) was about the watching itself breaking. This lesson is about a dashboard that works perfectly and still can't tell you what's wrong, because it's answering a different question from yours.

Each of the three signals answers one kind of question well:

| Signal | Answers | Cheap at | Bad at |
|---|---|---|---|
| **Metrics** | *Is something wrong, and how much?* | Huge volumes: a number every 15 seconds, forever | Which request, which user, why |
| **Traces** | *Where did this request spend its time?* | Following one request through many services | Totals and trends |
| **Logs** | *Why did this happen?* | Detail: the error message, the retry, the input | Being searched without a key to search by |

## Averages hide the tail

The SRE book warns that "a simple average can obscure these tail latencies, as well as changes in them." If 19 requests take 100 ms and one takes 2,000 ms, the average is 195 ms. It looks fine against a 300 ms target, and one user in twenty waits two seconds for every page. That's why latency SLOs are written in **percentiles**: the 99th percentile (p99) is the time 99 requests in 100 beat.

p99 tells you *that* something's slow. It can't tell you *which* service, because when one service waits on another, both look slow.

## Traces follow one request

A **trace** gives "the big picture of what happens when a request is made". It's made of **spans**, where each span "represents a unit of work or operation" and carries a name, start and end times, the id of its parent span, and the trace id it belongs to. When a service calls the next one, it passes that context along in a header (W3C `traceparent`). That's **context propagation**, "the core concept that enables Distributed Tracing": spans written by five different services join up into one tree.

## Logs that join up

A log line that says `timeout` is a needle in a haystack. A **structured log** is "a log with a defined, consistent schema or typed fields", and once a log record carries the trace id and span id, OpenTelemetry can "automatically correlate your existing logs with any active trace and span". You find the slow request in the trace, copy its trace id, and get exactly the log lines it wrote.

## What a metric costs

Metrics are cheap because they're aggregated: one number per time series, no matter how many requests it counts. But "every unique combination of key-value label pairs represents a new time series." A request counter labelled by method (5 values), status (6) and route (20) is 5 × 6 × 20 = **600** series. Add a `user_id` label with 50,000 users and it's **30 million** series. That's why the Prometheus docs say: "Do not use labels to store dimensions with high cardinality (many different label values), such as user IDs, email addresses". Per-user detail belongs in traces and logs, which store one record per request anyway.

<Callout kind="real">
OpenTelemetry is the vendor-neutral standard for producing all three signals: an SDK in each service, the trace context in each call, and an exporter that sends spans to a backend like Tempo or Jaeger. For .NET, Go, Java, JavaScript, PHP and Python there's zero-code instrumentation: it instruments the libraries you use (HTTP requests and responses, database calls, message queues) without changing your code. Your own code isn't covered, so the span attributes only you know matter are still yours to add.
</Callout>
