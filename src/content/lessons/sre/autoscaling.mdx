A Kubernetes **HorizontalPodAutoscaler** (HPA) keeps changing how many copies of a pod run, to hold a metric near a target. Its arithmetic fits on one line, from the Kubernetes docs:

> desiredReplicas = ceil( currentReplicas × currentMetricValue ÷ desiredMetricValue )

Four pods averaging 100% CPU against a 50% target: 4 × 100 ÷ 50 = 8 pods. Four pods at 25%: 2 pods. The rest of the docs is about the ways that simple line is slowed down on purpose:

- It runs **every 15 seconds** by default, not continuously.
- Inside a **tolerance** of 10% it does nothing, so it doesn't twitch at noise.
- CPU utilization is measured **against the pod's CPU request**, not its limit or the node.
- A pod that isn't **Ready** yet is set aside. When the result would be a scale-up, the controller "conservatively assumes that the not-yet-ready pods are consuming 0% of the desired metric". Slow-starting pods hold back the next scale-up as well as the first.
- Scaling **down** waits: it takes "the highest recommendation from within" a **5-minute** window, so a brief dip doesn't throw pods away that the next minute needs.

## The gap that drops requests

Add up the delays: up to 15 seconds before the HPA looks, then however long a new pod takes to pull its image, start, and pass its readiness probe. During that gap, the pods you already have take all of the spike. If the target is 90%, there's almost no headroom to absorb it, and the overflow is dropped.

## Scaling on the wrong thing

CPU is a good signal only when CPU is the work. A worker that spends its time waiting on a slow API, a database or a disk barely uses any CPU, so an HPA on CPU sees an idle service while its queue grows by the minute. Raising the limits doesn't help, because the metric never asks for more pods. Scale on what the work actually is: queue depth, requests in flight, or consumer lag. On Kubernetes that's usually [KEDA](https://keda.sh/), which can "drive the scaling of any container in Kubernetes based on the number of events needing to be processed" and works alongside the HPA rather than replacing it.

<Callout kind="real">
Kubernetes stops containers with SIGTERM and a grace period, then SIGKILL (see [processes and signals](/learn/linux/processes-and-signals/)), so scaling down also needs pods that finish their in-flight work when asked. And whoever owns `replicas` must be the only one setting it. If a GitOps sync re-applies `replicas: 1` while the HPA has scaled to four, three pods vanish at peak.
</Callout>
