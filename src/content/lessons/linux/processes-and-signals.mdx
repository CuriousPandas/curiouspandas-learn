A program on disk is just a file. Start it and you get a **process**: a running copy with its own number, the **PID**, and an owner. Your shell is a process. So is every command you type, for as long as it runs. `ps` lists them.

Processes don't get told what to do by being edited. They get sent **signals**: small numbered messages, delivered by the kernel. Four matter most:

| Signal | Number | Meaning | Can the program ignore it? |
|---|---|---|---|
| `SIGTERM` | 15 | "Please stop." What `kill` sends by default. | Yes - and good programs catch it, save their work and exit |
| `SIGINT` | 2 | What Ctrl+C sends to the program in front of you. | Yes |
| `SIGHUP` | 1 | "Your terminal went away." | Yes |
| `SIGKILL` | 9 | Not a message to the program at all. The kernel ends it. | **No.** It can't be caught, blocked or ignored |

## Exit codes: the number every process leaves behind

When a process ends it leaves an **exit status**, and your shell keeps the last one in `$?`. Zero means success. Anything else is some kind of failure, and a few values are worth knowing by sight:

- **127**: command not found. **126**: found, but not allowed to run.
- **128 + N**: killed by signal N. So **143** is SIGTERM (128 + 15), **130** is SIGINT (Ctrl+C) and **137** is SIGKILL.

SIGKILL always works, which is exactly why it is tempting and exactly why it is dangerous. The program gets no chance to finish a write, release a lock, delete its temporary files or tell its clients it is going. Send SIGTERM, give it a moment, and force it only if it is still there.

## The same numbers in Kubernetes

A container is a process too, and Kubernetes stops one the way you just did. To shut a pod down, the kubelet has the container runtime send **SIGTERM** to process 1 in each container, then waits a grace period - **30 seconds** unless the pod says otherwise. Anything still running after that gets **SIGKILL**.

So when [the restarts lesson](/learn/kubernetes/restarts/) shows a container with exit code 137, you now know what happened, if not yet why. Something sent signal 9: the kernel's out-of-memory killer, or Kubernetes itself after the process ignored SIGTERM or ran out of grace period. Exit code 143 means it ended because of SIGTERM - either it didn't handle it, or (like the JVM) it cleaned up and then reported the signal.

The sandbox's processes are simulated: time doesn't pass, so `sleep 300 &` runs until you stop it, and `wait` on a running job tells you so instead of hanging. Real `ps` shows more columns (CPU, memory, start time), and a real interactive shell reports a finished job at the next prompt.

<DoItForReal id="linux-signals-real" needs="terminal" xp={20}>

Watch the numbers for yourself. In bash or zsh:

```bash
sleep 300 &
kill %1          # SIGTERM
wait %1; echo $?  # 143

sleep 300 &
kill -9 %1       # SIGKILL
wait %1; echo $?  # 137
```

Then write a program that catches SIGTERM. `trap` runs a command when a signal arrives:

```bash
bash -c 'trap "echo saving...; exit 0" TERM; while true; do sleep 1; done' &
sleep 1   # give it a moment to set the trap, or the signal can beat it
kill %1   # prints "saving..."
wait %1; echo $?   # 0: it handled the signal
```
