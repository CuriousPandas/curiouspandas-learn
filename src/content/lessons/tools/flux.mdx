Flux has an off switch for each object it reconciles, and it's meant to be used: pause the automation, fix something by hand, resume. The catch is that the switch pauses the *reporting* too. A suspended release goes on showing the status of the last thing it did, and if that was a success, it keeps saying so while every new change waits.

## What it's for

[Git as the source of truth](/learn/platform/gitops/) showed what Flux does: controllers that keep pulling a desired state and applying it, Kustomizations for plain manifests and HelmReleases for charts, every `interval`. Every change becomes a commit, and the cluster keeps getting put back to match.

Sometimes you need it to stop. Mid-incident you want to scale something by hand without Flux reverting you, or you want a release left alone while you debug it. Flux's getting-started guide describes exactly that: "Suspending updates to a kustomization allows you to directly edit objects applied from a kustomization, without your changes being reverted by the state in Git." One command does it, `flux suspend`, and `flux resume` undoes it.

On tilt there's no GitRepository: Tilt applies the HelmRelease objects from your checkout, and Flux's helm-controller turns each into a Helm release. Tilt runs `flux install` with whatever Flux CLI you have, so your Flux version is your CLI's. These docs describe v2.10.

## How it quietly goes wrong

What suspension stops, in the docs' own words (v2.10):

- **HelmRelease:** "the controller will stop reconciling the HelmRelease, and changes to the resource or the Helm chart will not result in a new Helm release."
- **Kustomization:** "When a Kustomization is suspended, new Source revisions are not applied to the cluster and drift detection/correction is paused."

Nothing reconciles, so nothing rewrites the status either. The GitRepository docs say it outright for one case: if a suspended repository's stored artifact disappears, "this will not be reflected in the GitRepository's Status until it is resumed." The HelmRelease docs don't spell it out, but the same reasoning applies, and it's what you'll check below: a suspended HelmRelease's `Ready` condition describes the last release the controller made, not the spec you're looking at. Anything that reads only `Ready`, whether a dashboard, a script or a person glancing at it, sees a healthy release.

Two things do give it away:

- **The SUSPENDED column** in `flux get`. It's the one place in that output that says no one is acting on this.
- **Two numbers.** For a custom resource, Kubernetes increments `metadata.generation` on every change except to its metadata or status, so in practice on every spec change. Flux records `status.observedGeneration`, the latest generation that ended in a ready state, or stalled on an error it can't recover from without a person. The Kubernetes API conventions describe the field as the generation "most recently observed by the component responsible for acting upon changes". When the two differ, the status is describing an older spec.

Suspensions also outlive the incident. Flux's docs warn that writing `suspend: false` in git rules out "hot patching" a suspension with kubectl, because git would put it back. Turned round: if your git copy says nothing about `suspend`, a suspension someone set with `flux suspend` stays until someone runs `flux resume`. (That's our reading of the note: applying the file again doesn't clear a field the file never mentions.)

<Callout kind="trap">
Suspend pauses the work and freezes the report. A suspended HelmRelease keeps the `Ready` condition its last reconcile wrote, so it can read healthy for weeks while every commit since is ignored. Never read `Ready` alone: check SUSPENDED in `flux get`, or compare `metadata.generation` with `status.observedGeneration`.
</Callout>

The same shape exists one level down. The Kustomization docs describe an annotation or label, `kustomize.toolkit.fluxcd.io/reconcile: disabled`, that pauses reconciliation of a single object. Flux keeps reconciling everything around it, so the Kustomization can look busy and healthy while that one object is left as it is.

## Do it for real

<DoItForReal id="tool-flux-real" profile="gitops">

This uses Flagger's HelmRelease, which the `gitops` profile installs, because a small change to it is harmless. First the healthy picture, then suspend it:

```bash
flux get helmreleases -A
flux suspend helmrelease flagger -n istio-system
```

In your checkout, open `helm/flagger/base/helm-release.yaml` and change the memory *request* from `32Mi` to `48Mi`. Apply it the way Tilt does (use the `docker-desktop` overlay if that's your cluster):

```bash
kubectl apply -k ./helm/flagger/overlays/kind
flux get helmreleases -n istio-system
kubectl -n istio-system get helmrelease flagger -o jsonpath='{.metadata.generation} {.status.observedGeneration}{"\n"}'
helm get values flagger -n istio-system | grep -A2 requests
```

What to expect: SUSPENDED is True, the status still describes the last release, the generation is ahead of the observed generation, and Helm still has `32Mi`. The spec changed and nothing acted on it. Now resume and check again:

```bash
flux resume helmrelease flagger -n istio-system
kubectl -n istio-system get helmrelease flagger -o jsonpath='{.metadata.generation} {.status.observedGeneration}{"\n"}'
helm get values flagger -n istio-system | grep -A2 requests
```

The numbers match and Helm has `48Mi`. Put the file back (`git checkout` it) and apply it again.
