Someone deletes an old key from the vault, or moves it to a new path. The app keeps working. Its Kubernetes Secret still holds the last value External Secrets wrote. Nothing on the Secret, the Pod or the Deployment says anything has changed. The only error is on an object most people never look at: the ExternalSecret, which now reads `SecretSyncedError`.

## What it's for

[Deleted is not gone](/learn/security/secrets-in-git/) ended with a rule: keep secrets out of the repository, and read them from a secrets manager instead. The **External Secrets Operator** (ESO) connects the two. The real value lives in a store: a vault, a cloud secret manager, 1Password. The repository holds only a pointer to it.

- A **SecretStore** (one namespace) or **ClusterSecretStore** (any namespace) says how to reach the provider and log in to it.
- An **ExternalSecret** says *which* values to fetch, and the name of the Kubernetes Secret to write them into.
- The operator fetches the values and writes an ordinary Kubernetes Secret, which pods use as they always have.

It's the [desired-state loop](/learn/kubernetes/desired-state/) again, with one difference that matters. The docs say it directly: "ESO is pull-based and does not watch providers, so only Periodic polls (at each interval)." A change in the vault reaches the cluster only at the next refresh. One default here surprises people: "Due to backwards compatibility, setting a refresh interval of 0 will result in the same behavior as CreatedOnce". Zero means *sync once*, not *sync constantly*.

On tilt, the `gitops` profile installs ESO chart 2.10.0 as a Flux HelmRelease in the `external-secrets` namespace. The repo ships a working store on purpose: a ClusterSecretStore called `dev-fake`, using the fake provider. In its docs' words, "This provider returns static key/value pairs and nothing else." Its values sit in the manifest, as public as any other file in the repo. It's there to prove the wiring, not to keep anything secret. Tilt's startup check waits for the `demo-credentials` ExternalSecret to be Ready and for its Secret to exist. A comment in the repo explains why: an operator with no working store reports healthy while reconciling nothing.

## How it quietly goes wrong

An ExternalSecret's `target.deletionPolicy` says what happens when the provider has no value to give. The default is `Retain`, and the docs define it in two sentences: "Retain will retain the secret if all provider secrets have been deleted. If a provider secret does not exist the ExternalSecret gets into the SecretSyncedError status."

The second sentence is the trap. The Kubernetes Secret keeps the last value it had. The error goes on the ExternalSecret. In the v2.10.0 controller, any error fetching data from the provider marks the ExternalSecret failed *before* the Secret is touched. That covers a deleted key, and also a store that can't be reached or whose credentials have expired. Its Ready condition goes to `False`. The `Last Sync` column, the ExternalSecret's `status.refreshTime`, stops moving, because only a successful sync updates it.

Here is how that plays out in practice. This is a constructed example. A team rotates a database password, writes the new one under a new path, and deletes the old entry. Nobody updates the ExternalSecret. The app carries on with the old password, which still works. Two weeks later the database revokes the old password, and the app falls over for no reason anyone can see. The warning had been sitting on the ExternalSecret all along.

<Callout kind="trap">
A Kubernetes Secret has no status, so it can't tell you it's out of date. With the default `deletionPolicy: Retain`, a value that's gone from the store, or a store ESO can't reach, leaves the Secret holding its last value, and the error sits only on the ExternalSecret. Alert on the ExternalSecret's Ready condition (the operator exports `externalsecret_status_condition`), not on whether the Secret exists.
</Callout>

The other policies trade this risk for a different one. `Delete` removes the Secret once all of its provider values are gone. You can't miss that, and it's also an outage the next time a pod starts. `Merge` removes the missing keys and keeps the Secret. Neither is wrong. Pick one on purpose, and watch the ExternalSecret either way.

## Do it for real

<DoItForReal id="tool-external-secrets-real" profile="gitops">

Bring up the `gitops` profile and look at the store and the ExternalSecret tilt ships:

```bash
PROFILE=gitops ./scripts/platform.sh up                          # stays running; use a second terminal
kubectl get clustersecretstore dev-fake                          # READY True
kubectl -n external-secrets get externalsecret demo-credentials  # SecretSynced, READY True
```

Leave `dev-fake` alone: the platform's own check depends on it. Make a small store of your own instead. It uses the same fake provider, with a token in it, and an ExternalSecret that copies the token:

```bash
kubectl apply -f - <<'EOF'
apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: stale-demo
  namespace: default
spec:
  provider:
    fake:
      data:
        - key: /demo/token
          value: token-from-monday
        - key: /demo/unused
          value: placeholder
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: stale-demo
  namespace: default
spec:
  refreshInterval: 1h
  secretStoreRef:
    kind: SecretStore
    name: stale-demo
  target:
    name: stale-demo
  data:
    - secretKey: token
      remoteRef:
        key: /demo/token
EOF
kubectl -n default get externalsecret stale-demo                              # SecretSynced, READY True
kubectl -n default get secret stale-demo -o jsonpath='{.data.token}' | base64 -d; echo   # token-from-monday
```

If the first `get` doesn't show Ready yet, give it a few seconds and run it again. Now delete the token *at the provider*, and ask for a refresh straight away instead of waiting an hour:

```bash
kubectl -n default patch secretstore stale-demo --type=json -p '[{"op":"remove","path":"/spec/provider/fake/data/0"}]'
kubectl -n default annotate es stale-demo force-sync=$(date +%s) --overwrite
kubectl -n default get externalsecret stale-demo                              # SecretSyncedError, READY False
kubectl -n default get secret stale-demo -o jsonpath='{.data.token}' | base64 -d; echo   # still token-from-monday
```

That's the trap: the value is gone from the store, and the Secret still holds it. `kubectl -n default describe externalsecret stale-demo` shows the failure in its events. Run the first `get` again in a few minutes: `Last Sync` is still the time of the last *good* sync. Clean up afterwards. The default creation policy, `Owner`, means the Secret is deleted along with its ExternalSecret:

```bash
kubectl -n default delete externalsecret stale-demo
kubectl -n default delete secretstore stale-demo
```
