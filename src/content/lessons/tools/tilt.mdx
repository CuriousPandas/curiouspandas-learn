You edit a manifest, save, and look at the Tilt dashboard. Everything is green. The change never reached the cluster, and it won't until someone forces that resource to run or restarts Tilt, because the resource that applies that file was never told to watch it.

## What it's for

**Tilt** runs the inner loop of working on a cluster: it watches your files and, when one changes, rebuilds and redeploys whatever depends on it, then shows every resource's state and logs in one dashboard (`http://localhost:10350`). You describe the work in a `Tiltfile`, written in Starlark, a dialect of Python.

On the tilt platform, Tilt *is* the orchestrator. `./scripts/platform.sh up` from [Run the real platform](/learn/platform/bring-it-home/) creates the kind cluster and then runs `tilt up`. The root `Tiltfile` is a short table of contents that includes one file per profile tier (`tilt/core.tilt` for `minimal`, and so on). Most of what those files define is not an image build. It's a **local_resource**: a command run on your machine, usually `kubectl apply -k` on a directory, followed by checks that it worked.

Tilt also watches `tilt-config.json` with `watch_file`, which is why turning an app on in that file makes Tilt reload by itself.

## How it quietly goes wrong

A local resource re-runs only when one of its **deps** changes. Tilt's docs say it directly: "By default, a local resource without deps runs only once: on tilt up (and any time you change its definition in your Tiltfile)." The API reference describes `deps` as the files Tilt watches, and it "will run the cmd when they change".

So the command, and the files that command applies, are two separate things. Tilt knows the first. It knows the second only if you list them in `deps`. A resource that runs `kubectl apply -k ./helm/something` with no `deps` applied that directory once, went green, and stays green whatever you do to the directory afterwards.

The platform hit this twice and wrote down both. In `tilt/core.tilt`, the gateway resource now has `deps`, with the reason beside it: edits to "the gateway, the certificate SANs or the HTTPS redirect never reached the cluster while Tilt stayed green." It was found when the live HTTPS redirect differed from the repo. `tilt/observability.tilt` has the same story for ServiceMonitor fixes that only reached clusters started after them. The same comments flag a second, smaller trap: relative `deps` paths resolve against the included file, not the repo root, so the platform builds them from `ROOT`.

It isn't fully fixed. At the commit we read, several resources still apply a directory that nothing watches: no `deps`, and the Tiltfile doesn't load that directory itself. Among them are `cert-manager` and `istio` in the `minimal` tier and `kiali` and `metrics-server` in `observability`. (Others, such as `prometheus`, also lack `deps` but are covered another way: the Tiltfile loads their directories with `kustomize()`, and the API reference says a directory passed to `kustomize()` is watched.) So an edit under `helm/cert-manager/` reaches the cluster only when you force that resource to run or restart Tilt.

<Callout kind="trap">
Green on a Tilt local_resource means *the last run succeeded*, not *the cluster matches your files*. Without `deps`, the last run was at `tilt up`. Check what a resource watches before trusting it with an edit, and when it watches nothing, force it with `tilt trigger RESOURCE`, which the docs say will force a full rebuild.
</Callout>

## Do it for real

<DoItForReal id="tool-tilt-real" profile="minimal">

With the platform up (`./scripts/platform.sh up`) and the Tilt dashboard open at `http://localhost:10350`. The `hello-world` resource lists `examples/hello-world` in its `deps`; `cert-manager` lists nothing. Watch the difference. (If you started Tilt with a non-default `TILT_PORT`, add `--port` with that number to each `tilt` command.)

```bash
tilt logs hello-world
# edit examples/hello-world/deployment.yaml: change the PODINFO_UI_MESSAGE value, then save
tilt logs -f hello-world
# Ctrl-C, then add a comment line to helm/cert-manager/overlays/kind/kustomization.yaml and save
tilt logs cert-manager
tilt trigger cert-manager
tilt logs -f cert-manager
```

The first edit makes `hello-world` run again by itself, and `https://hello.localhost` shows your new message. The second makes nothing happen: no new log lines, still green. `tilt trigger` makes it run, and since a comment changes nothing, it applies the same thing it applied before.

Then put both files back. Undo the message edit: `./scripts/platform.sh hello` and the browser check look for the original text, so they fail until you do. Saving it makes `hello-world` re-run again. Undo the comment too; Tilt won't notice that one either.

</DoItForReal>
