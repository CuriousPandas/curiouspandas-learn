So far every commit has lived in one repository: yours. Real projects have many copies of the same history - one on each laptop, and usually one on a server everybody agrees to share, like GitHub. Git calls those other copies **remotes**. When you clone, git names the one you cloned from **origin**.

Nothing syncs by itself. Three commands move commits between copies:

| Command | What it moves | What it changes |
|---|---|---|
| `git fetch` | their new commits, into your repository | only `origin/main`, your *picture* of their branch |
| `git pull` | the same, then merges | your current branch too |
| `git push` | your new commits, to them | their branch - if it's safe |

Pro Git is careful about fetch: it only downloads the data, and doesn't merge it with your work or change what you're working on. That makes `fetch` always safe to run. `pull` is `fetch` plus a merge - the same merge you met in [Conflicts are honesty](/learn/git/conflicts/).

## When someone pushed first

Pro Git describes the everyday collision: if you and someone else clone at the same time, and they push and then you push, your push will rightly be rejected. You have to fetch their work and fold it into yours before you're allowed to push.

Here is exactly what git 2.54 printed when the second push lost the race against a real remote:

```text
 ! [rejected]        main -> main (fetch first)
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
```

After a `git fetch` but before merging, the same push is refused as `(non-fast-forward)`, with the hint that the tip of your current branch is behind. After merging `origin/main`, it goes through.

<Callout kind="trap">
`git push --force` makes the rejection go away by overwriting the remote branch with yours. The git-push docs warn that it can make the remote lose commits, and that blindly force-pushing will lose other people's work. If you ever truly need it, `--force-with-lease` refuses when the remote has moved since you last fetched.
</Callout>

## Pull requests: changes that get read

Pushing straight to `main` means every change reaches everyone unreviewed. A **pull request** pushes your work to a branch instead and asks for it to be merged. GitHub's docs describe the review as a chance for people to comment on changes, suggest improvements, and approve or request changes before the code is merged.

Teams make that the only way in with **protected branches**. GitHub's settings include requiring pull request reviews and requiring status checks to pass before merging. The status checks are your [pipeline](/learn/delivery/pipelines/): the same checks, on every proposed change, before it can land.

A good review is mostly questions. Not "this is wrong", but "what happens if this list is empty?" The author knows the change best. The reviewer's job is to be the first person who didn't write it.

<Callout kind="real">
This lesson's sandbox doesn't simulate a second repository - the git playground has one repository and no network. The push race above was reproduced with the real git binary, two clones and a local bare repository, which is also the cheapest way to try it yourself (below).
</Callout>

<DoItForReal id="git-collaborate-real" needs="terminal">

No account needed: a bare repository on your own disk is a perfectly good remote.

```bash
git init --bare remote.git
git clone remote.git alice && git clone remote.git bob
cd alice && git commit --allow-empty -m "base" && git push origin HEAD:main && cd ..
cd bob && git fetch && git switch main && cd ..
cd alice && git commit --allow-empty -m "X" && git push origin HEAD:main && cd ..
cd bob && git commit --allow-empty -m "Y" && git push origin main     # rejected (fetch first)
git pull --no-rebase --no-edit && git push origin main               # merged, accepted
git log --oneline --graph
```

Then open a real pull request in [CuriousPandas/practice](https://github.com/CuriousPandas/practice), a repository that exists for exactly this: fork it, add `visitors/<your-username>.md` on a branch, push, and open a pull request against its `main`. Its `visitor-file` check is your status check - if it goes red, read why, fix it on the same branch and push again. Its `main` is protected like the quiz above: one approval and a green check. Practice pull requests are closed after 14 days; that is not a rejection.

</DoItForReal>
