`kubectl create ingress shop --rule='shop.localhost/*=web:80'` prints `created`. `kubectl get ingress` lists it, with the host and port you asked for. The ADDRESS column is empty. It stays empty. `kubectl describe ingress` shows the rule, the backend, even the pod IPs behind the Service, and ends with `Events: <none>`. Nothing is wrong with the object. There is just nothing on the other end of it.

## Three parts, one of them missing

An **Ingress** holds HTTP routing rules: a host, a path, and the Service and port to send matching requests to. It doesn't route anything itself. The docs are blunt: "You must have an Ingress controller to satisfy an Ingress. Only creating an Ingress resource has no effect."

An **Ingress controller** is a proxy running in the cluster (in pods, like anything else) that watches Ingress objects and configures itself to match. When it takes on an Ingress, it usually writes its own address into the Ingress's status, and that's the ADDRESS column. No controller, no address. The reverse doesn't hold: an empty ADDRESS doesn't prove nobody is serving it. A controller can watch an Ingress and still write no address, because it has none to write or isn't set up to publish one. tilt has an example, below.

An **IngressClass** says which controller an Ingress is for. An Ingress names one in `spec.ingressClassName`. `kubectl explain` describes the link as "controller -> IngressClass -> Ingress resource". If the field is empty, a class marked default with the annotation `ingressclass.kubernetes.io/is-default-class: "true"` is filled in, but, the docs say, only for "new Ingresses without an ingressClassName field specified". An Ingress created before anyone marked a default stays class-less.

## Frozen, and why Gateway API won

The Ingress page opens with a note: "The Kubernetes project recommends using Gateway instead of Ingress. The Ingress API has been frozen." It also says the project "has no plans to remove Ingress from Kubernetes", so existing Ingresses keep working. They just won't get new features.

You've already met what replaced it in [Gateway API](/learn/tools/gateway-api/). Compare the failure. A route that attaches to nothing has an empty `status.parents`, and the Gateway API docs tell you to read it. An Ingress that nothing serves has an empty `status.loadBalancer`, and nothing tells you anything. Behaviour beyond the basics was left to annotations, which each controller defines for itself, so the same Ingress can mean different things on different controllers.

TLS shows how far controllers drift apart. An Ingress's `secretName` is only a name, with no namespace field, and controllers disagree about where to look for it. Istio's Ingress guide says the Secret "must exist in the namespace of the istio-ingressgateway deployment (typically istio-system)", not the Ingress's. tilt's own history has a cousin of this failure. Before Gateway API, tilt's apps were routed by Traefik's own IngressRoute objects (a Traefik custom resource, not a Kubernetes Ingress), and the comment now at the top of tilt's `helm/*/httproute.yaml` files (`helm/argocd` among them) records that "each app named a TLS secret that only existed in the traefik namespace and silently fell back to the default cert store".

## Give it something to talk to

In the sandbox there's no Ingress controller until you install one. Create the Ingress first and watch it sit there.

</Callout>

## What serves Ingress on tilt

Nothing, as we found on the running platform. `kubectl get ingressclass` returns `No resources found`. tilt routes everything with Gateway API, through Istio. Istio can serve Ingress objects, and its control plane does watch them: the istiod log on tilt says `Starting ingress controller`, and Istio's mesh config there has `ingressClass: istio` and `ingressControllerMode: STRICT`, so it takes Ingresses of class `istio`. The same config says `ingressService: istio-ingressgateway`, which Istio's reference calls the "Name of the Kubernetes service used for the istio ingress controller", and tilt has no Service by that name. Nor does it run the ingress gateway that Istio's own Ingress guide relies on: `kubectl -n istio-system get pods -l istio=ingressgateway` finds none. We created an Ingress with no class and one with `--class=istio`. Neither got an address or an event, and `https://<host>.localhost` for each returned a 404 from tilt's Gateway, which had no route for those hostnames. So the `istio` one was watched by a controller and still showed an empty ADDRESS.

<DoItForReal id="kube-ing-real" profile="minimal">

These ran on tilt (Kubernetes 1.36.1, Istio 1.28.3). The Ingresses go in a scratch namespace, `ing-lab`, with a `web` Service of its own, so nothing is added to `hello` or any other namespace tilt uses. The HTTPRoute line only reads `hello`.

```bash
kubectl get ingressclass                                     # No resources found
kubectl -n istio-system get pods -l istio=ingressgateway     # No resources found
kubectl create namespace ing-lab
kubectl -n ing-lab create deployment web --image=ghcr.io/stefanprodan/podinfo:6.9.1 --port=9898
kubectl -n ing-lab expose deploy web --port=80 --target-port=9898
kubectl -n ing-lab create ingress web-ing --rule='ing-lab.localhost/*=web:80'
kubectl -n ing-lab create ingress web-istio --class=istio --rule='ing-lab-istio.localhost/*=web:80'
kubectl -n ing-lab get ingress                               # CLASS <none> and istio, ADDRESS empty for both
kubectl -n ing-lab describe ingress web-ing                  # the backend's pod IP, and Events: <none>
curl -sk -o /dev/null -w '%{http_code}\n' https://ing-lab.localhost/     # 404, from tilt's Gateway
kubectl -n hello get httproute hello -o jsonpath='{.status.parents[0].conditions[*].type}'; echo   # Accepted ResolvedRefs ...: Gateway API reports
kubectl explain ingress.spec.tls.secretName                  # a name, no namespace
kubectl delete namespace ing-lab
```

</DoItForReal>

## What to remember

- An Ingress is rules. A controller makes them real and usually writes the ADDRESS; with no controller, nothing happens and nothing says so. A request through it is the only proof.
- `ingressClassName` ties an Ingress to a controller. A default class is filled in only on new Ingresses.
- The Ingress API is frozen. Kubernetes recommends Gateway API, which reports attachment in status.
- tilt serves no Ingress at all: no IngressClass, and no Istio ingress gateway.
