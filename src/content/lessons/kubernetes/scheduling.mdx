You ask for three replicas. Two start. The third sits in **Pending** and stays there. Nothing crashed and nothing is red. `kubectl get pods` shows the word Pending and nothing else.

Pending means the pod exists but no node has been chosen for it. The **scheduler** keeps trying, and each time it fails it records *why* as an **event** on the pod. You only see events if you ask for them.

## Requests, not usage

The scheduler places pods by what they **request**, not by what they actually use. Every container can declare `requests.cpu` and `requests.memory`. The scheduler adds up the requests already placed on each node and won't go past the node's capacity. From the Kubernetes docs:

> although actual memory or CPU resource usage on nodes is very low, the scheduler still refuses to place a Pod on a node if the capacity check fails.

That surprises people the first time. A node can sit at 3% CPU and still be "full", because everything on it *asked* for a lot. It's deliberate: a request is a reservation for your peak, not a guess at your average.

## Find it, read it, fix it

This cluster has two nodes with 2 CPUs (2000m) each. Someone deployed `big` with three replicas, each requesting 1500m. Work out why one won't start, then fix it *without* scaling down.

<KubeSim mission="kube-pending" title="Three big pandas, two small nodes" />

<Callout kind="tip">
`m` means millicores: 1000m is one CPU. `1500m` asks for one and a half CPUs, reserved for that pod whether it uses them or not.
</Callout>

<Callout kind="trap">
If your fix still doesn't fit *next to* the old pods, the update itself waits. With the default rolling strategy, new pods must start before old ones are removed, and they need room to do it. Choose a request that fits in what's left on a node.
</Callout>

<Callout kind="real">
Real scheduling checks much more than CPU and memory: taints and tolerations, node selectors and affinity, topology spread, volume zones and more. The event message lists every reason. In v1.36 it begins like `0/3 nodes are available: 1 node(s) had untolerated taint(s), 2 Insufficient memory.` and goes on with the scheduler's verdict on preemption. The habit is the same: describe the pod and read the last lines.

The bar and the `requested` figure on each node in the sandbox's picture are its own drawing. A real `kubectl get nodes` has no CPU column, and neither does the sandbox's: the numbers are in `kubectl describe node`, under "Allocated resources", on both.
</Callout>

<DoItForReal id="kube-sched-real">

There's no dedicated tilt lab for this one; the minimal platform is enough. In a scratch namespace, ask for more CPU than any laptop has. Run on 2026-11-03 against Kubernetes v1.36.1:

```bash
kubectl create namespace sched-lab
kubectl -n sched-lab create deployment big --image=nginx:1.27-alpine --replicas=2
kubectl -n sched-lab rollout status deploy/big
kubectl -n sched-lab set resources deployment big --requests=cpu=100   # 100 whole CPUs
kubectl -n sched-lab get pods        # one Pending, beside two Running from the first template
kubectl -n sched-lab get events --field-selector reason=FailedScheduling
kubectl describe node | grep -A9 "Allocated resources"
kubectl delete namespace sched-lab
```
