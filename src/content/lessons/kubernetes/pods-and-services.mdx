You create a Service of `type: LoadBalancer`. `kubectl get svc` shows it straight away, with a cluster IP and a port, and in the EXTERNAL-IP column the word `<pending>`. A minute later it still says `<pending>`. On a laptop cluster it will say that until you delete it. `kubectl describe svc` lists `Events: <none>`. Nothing failed, so nothing reports a failure.

This lesson is about where traffic goes inside a cluster: how pods get addresses, what a Service adds on top, and the two quiet ways a Service lets you down.

## Every pod gets an address

The Kubernetes docs set out the network model in a few rules. "Each pod in a cluster gets its own unique cluster-wide IP address." And "All pods can communicate with all other pods, whether they are on the same node or on different nodes", "directly, without the use of proxies or address translation (NAT)."

Kubernetes itself doesn't build that network. In the docs' words, "the pod network itself is managed by a pod network implementation", and on Linux these "are often called CNI plugins", after the **Container Networking Interface** they plug into. On a kind cluster the plugin is kindnet. Each node gets a slice of the pod address range, such as `10.244.1.0/24`, and the plugin gives every new pod on that node an address from it. You met that notation in [IP addresses and subnets](/learn/network/ip-and-subnets/).

Pod addresses don't last. A replacement pod gets a new name and a new IP, which is why the [Service that selects nobody](/learn/tools/kubernetes/) lesson needed Services in the first place.

## What each Service type adds

A **Service** gives a changing set of pods one stable address. It finds its pods by label selector, lists their addresses in EndpointSlices, and each node's service proxy (kube-proxy, on kind) rewrites traffic for the Service's address to one of those pods. Each type builds on the one before:

- **ClusterIP**, the default, "makes the Service only reachable from within the cluster." It gets a virtual IP, like `10.96.98.211`, that no pod owns.
- **NodePort** "Exposes the Service on each Node's IP at a static port". The port comes from a range that defaults to 30000-32767, and "To make the node port available, Kubernetes sets up a cluster IP address" as well.
- **LoadBalancer** "Exposes the Service externally using an external load balancer." It gets a node port too. Then, the docs continue, "Kubernetes does not directly offer a load balancing component; you must provide one, or you can integrate your Kubernetes cluster with a cloud provider."
- **Headless** isn't a type of its own. It's a ClusterIP Service with `clusterIP: None`: no virtual IP, and no proxying. DNS answers with the pods' own addresses instead. The [cluster DNS](/learn/kubernetes/cluster-dns/) lesson uses one.

Two port numbers matter. `port` is what clients connect to on the Service. `targetPort` is where the traffic goes on the pod. If you leave `targetPort` out, the docs say, "the targetPort is set to the same value as the port field."

## Pending, and refused

On kind, nothing implements LoadBalancer unless you install it. The kind docs have a whole guide to "get service of type LoadBalancer working in a kind cluster using Cloud Provider KIND". tilt doesn't install it. Its `kind/cluster.yaml` publishes a fixed node port to your machine instead, and the comment there says why: "There is no load balancer on kind, so without this mapping the gateway is healthy and unreachable."

The second fault is quieter. A Service can select the right pods, have endpoints, and still have every connection refused, because `targetPort` names a port the pods never opened. The EndpointSlice faithfully lists the pod IPs with the wrong port. `kubectl get svc` looks perfect.

Here, the `web` Service in namespace `shop` has been waiting for a load balancer for ten minutes, and it has a second fault. Find both, then do a blue/green switch with nothing but a selector.

<Callout kind="trap">
A Service with endpoints isn't proof that anything listens. EndpointSlices are built from labels and readiness, and nobody checks that `targetPort` is a port the container opened. The only test is a request. Make it from inside the cluster first, so the load balancer and node ports are out of the picture.
</Callout>

## Ready, not just running

Endpoints carry readiness, too. Each endpoint has a `ready` condition, which follows the pod's Ready condition, and a failing readiness probe turns that false. A pod whose readiness probe fails is still Running and isn't restarted; it just stops getting new traffic. In the sandbox, the panda images copy podinfo's switch: `curl -X POST http://POD-IP:8080/readyz/disable` from the client pod makes that pod fail its probe. The switch only matters to a pod that has a readiness probe on `/readyz`. tilt's `hello` Deployment has one. A pod made with `kubectl create deployment` has none, so it takes the request (202) and stays 1/1: we checked.

One detail surprised us on a real cluster. `kubectl get endpointslices` still listed the unready pod's address. Readiness is a condition on each endpoint, so you see it with `-o yaml` (`ready: false`), while `kubectl describe svc` lists only the ready addresses.

<Callout kind="real">
The sandbox applies changes instantly and uses kindnet and kube-proxy's behaviour, measured on Kubernetes 1.36.1. Real clusters take a moment to update EndpointSlices, and some plugins replace kube-proxy with their own service proxy. The sandbox also lets your machine reach a node's IP directly; whether a real one can depends on how Docker runs on it, which is why tilt publishes fixed node ports to localhost instead. In a namespace that is in Istio's ambient mesh, such as tilt's `hello`, a refused connection looks different: the local ztunnel accepts it first, so curl reports `(56) Recv failure: Connection reset by peer` instead of `(7) ... Could not connect to server`.
</Callout>

<DoItForReal id="kube-svc-real" profile="minimal">

These ran on tilt with Kubernetes 1.36.1. The first commands only read tilt's own objects. Everything that creates something does it in a scratch namespace, `svc-lab`, with the same podinfo image `hello` runs, and deleting the namespace at the end removes it all. It is outside the mesh, so a refused connection shows as the sandbox's `(7)`; in `hello`, which is in the mesh, it would be `(56) ... Connection reset by peer`.

```bash
kubectl -n hello get svc hello -o wide            # port 80, selector app.kubernetes.io/name=hello
kubectl -n hello get deploy hello -o jsonpath='{.spec.template.spec.containers[0].ports}'; echo   # the "http" port is 9898
kubectl -n istio-system get svc                   # localhost-gateway-nodeport: 80:30080, 443:30443
kubectl -n hello get pods -o wide                 # pod IPs from 10.244.x.0/24

kubectl create namespace svc-lab
kubectl -n svc-lab create deployment web --image=ghcr.io/stefanprodan/podinfo:6.9.1 --port=9898
kubectl -n svc-lab expose deploy web --name=web-lb --type=LoadBalancer --port=80 --target-port=9898
kubectl -n svc-lab get svc web-lb                 # EXTERNAL-IP <pending>, and a node port
kubectl -n svc-lab describe svc web-lb | tail -3  # Events: <none>
kubectl -n svc-lab get svc web-lb                 # a minute later: still <pending>
kubectl -n svc-lab expose deploy web --port=80 --target-port=8080       # the wrong port
kubectl -n svc-lab run client --image=curlimages/curl:8.11.1 --restart=Never --command -- sleep 3600
kubectl -n svc-lab wait --for=condition=Ready pod/client
kubectl -n svc-lab exec client -- curl -sS -m 5 http://web               # curl: (7) ... Could not connect to server
kubectl -n svc-lab get endpointslices                                    # PORTS 8080: endpoints, wrong port
kubectl delete namespace svc-lab
```

## What to remember

- Every pod gets its own IP from its node's slice of the pod range; the CNI plugin does that, not Kubernetes itself.
- ClusterIP is reachable only inside the cluster. NodePort adds a port on every node. LoadBalancer adds a load balancer that something else must provide, and waits silently if nothing does.
- A Service with endpoints can still refuse every connection: check `targetPort` against the container's port.
- A selector decides which pods get traffic. Switching it is a blue/green deploy.
