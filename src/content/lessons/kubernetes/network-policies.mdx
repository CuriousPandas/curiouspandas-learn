The plan was simple: deny everything in namespace `shop`, which wasn't in a service mesh, then allow what the app needs. The deny went in, and every request in the namespace began to fail with `curl: (6) Could not resolve host: api`. Not "connection refused", not a timeout to the database. The apps couldn't even look up a name, because asking DNS is a network connection too, and it had just been denied.

## How NetworkPolicy decides

The [cluster access](/learn/security/cluster-access/) lesson explained what a NetworkPolicy is, and its first trap: a policy nothing enforces. Here are the rules for writing one, from the Kubernetes docs.

- **No policy, no limits.** "By default, a pod is non-isolated for ingress; all inbound connections are allowed." The same goes for egress (outbound).
- **Selected means isolated.** A pod is isolated for ingress once any policy that selects it has `Ingress` in its `policyTypes`. Then "the only allowed connections into the pod are those from the pod's node and those allowed by the ingress list of some NetworkPolicy that applies to the pod". Egress works the same way.
- **Policies only add.** "Network policies do not conflict; they are additive." There is no deny rule. A default deny is a policy that selects pods and allows nothing.
- **Both ends must agree.** "For a connection from a source pod to a destination pod to be allowed, both the egress policy on the source pod and the ingress policy on the destination pod need to allow the connection."

Policies match pods, not Services. With kube-proxy, as on kind, a request to a Service's IP is rewritten to a pod's IP and port before the policy sees it, so a rule for the api Service on port 80 names the pods' port, 8080. The docs leave that order to the implementation. For traffic into and out of the cluster they say it "is not defined whether this happens before or after NetworkPolicy processing", and they don't promise it for a Service's IP either, so check what your plugin does.

And if `policyTypes` is left out, the docs say, "Ingress will always be set and Egress will be set if the NetworkPolicy has any egress rules". A policy written to restrict egress can isolate ingress too.

## One list item, or two

The single most common mistake is a dash. These look almost the same:

```yaml
  egress:
  - to:
    - namespaceSelector:          # one item, two selectors:
        matchLabels:              # pods labelled k8s-app=kube-dns
          kubernetes.io/metadata.name: kube-system
      podSelector:                # AND in namespace kube-system
        matchLabels:
          k8s-app: kube-dns
```

```yaml
  egress:
  - to:
    - namespaceSelector:          # two items: any pod in kube-system,
        matchLabels:
          kubernetes.io/metadata.name: kube-system
    - podSelector:                # OR any kube-dns pod in this namespace
        matchLabels:
          k8s-app: kube-dns
```

The docs show the same pair and add: "When in doubt, use kubectl describe to see how Kubernetes has interpreted the policy." `describe` prints one `From:` (or `To:`) line per list item, so two items show as two lines.

Out of the mesh, allowing DNS fixes the error message, not the app. After `allow-dns.yaml`, names resolve and every request still times out, because the egress to api and the ingress into api are both still denied. <Callout kind="tip">
A blocked connection is dropped, not refused, so it shows as a timeout. Without `-m 5`, curl on tilt waited 2 minutes 20 seconds before giving up. Use a short timeout when testing policies, and read a timeout as "something dropped it", not "nothing listens". One catch, measured on tilt: when DNS itself is blocked, the resolver takes about five seconds to give up, so `-m 5` runs out first and curl says `(28) Resolving timed out` instead of `(6) Could not resolve host`. Both mean the name never resolved.
</Callout>

## What the ambient mesh changes

tilt's `hello` namespace is in Istio's ambient mesh (`istio.io/dataplane-mode: ambient`, from [the Istio lesson](/learn/tools/istio/)). Three things change there.

**The port is 15008, at both ends.** Traffic between mesh pods doesn't travel on the app's port. The Istio docs: "ambient's secure L4 overlay will tunnel traffic between your pods over port 15008", and "NetworkPolicy is enforced on the host, outside the pod", so a policy that lets inbound traffic in on the app's port only "will have to add an exception to that NetworkPolicy for port 15008". That page talks about inbound traffic. We tested both directions on tilt (Istio 1.28.3, kindnet), in a scratch namespace we enrolled in the mesh. With ingress allowing port 9898 only, a request from a mesh pod timed out, and adding 15008 let it through. Egress was the same: a client whose egress allowed only 9898 to web timed out three times out of three, adding 15008 gave 200, and 15008 on its own was enough. Test with a new client pod. One that had already talked to web before the rule kept getting 200; our guess, not proven, is that ztunnel reused a tunnel it already had open.

**DNS keeps working.** In ambient mode, ztunnel answers DNS. Istio's docs: "Ambient mode DNS proxying is enabled by default in ambient mode from Istio 1.25 onwards", and when the proxy can handle a request, "it will directly return a response to the application, avoiding a roundtrip to the upstream DNS server." tilt's Istio has it switched on. So in the mesh, a default deny for egress didn't stop Service names resolving. `curl -v http://web` printed `Host web:80 was resolved` and `Connected to web`, then `(28) Operation timed out ... with 0 bytes received`. With a longer `-m` it ended in `(56) Recv failure: Connection reset by peer` after ten to fifteen seconds. Names ztunnel doesn't know, such as a name that exists nowhere or a pod's own DNS name, go on to CoreDNS, which the deny blocks, and those still fail with `(28) Resolving timed out` or `(6) Could not resolve host`. So the clue that points at DNS out of the mesh is gone, and a default deny looks like a connection that hangs. That the answer gets past the policy is measured. Why is our reading of the docs: the proxy answers from inside the pod's own network, so the answer never crosses the point where policy is enforced.

**Probes come from somewhere else.** Out of the mesh, kubelet's probes come from the pod's own node, and the docs guarantee that traffic: an isolated pod still accepts connections "from the pod's node", and pods cannot "block access from their resident node". In ambient mode the probes reach the pod from the fixed address 169.254.7.127 instead, and the Istio page warns: "Depending on your CNI, kubelet probes and link-local addresses may be ignored by this policy, or be blocked by it." On tilt's kindnet they weren't blocked. Under a default deny for ingress, a pod with a real readiness probe stayed Ready, and a new pod became Ready under it. On another plugin they may fail, and then the pods go 0/1 with no policy error anywhere. Istio's fix is to allow `169.254.7.127/32` with an `ipBlock`.

<Callout kind="real">
Two things the sandbox simplifies. It applies a policy instantly; the docs warn that "it may take some time for a network plugin" to enforce a new one. And it treats every connection as new. The docs say that whether a new policy cuts a connection already open "is implementation defined". On tilt, in the mesh, requests kept succeeding for about thirty seconds after a default deny went in, then timed out, with one more success a minute later; three minutes on, thirty requests in a row all timed out. Our guess, not proven, is that ztunnel was reusing connections it had opened before the policy. Out of the mesh, the first request after the policy timed out, and so did the next thirty.
</Callout>

<DoItForReal id="kube-np-real" profile="minimal">

We ran these on tilt (Kubernetes 1.36.1, kindnet, Istio 1.28.3 ambient), in a scratch namespace rather than `hello`, which other lessons use. Use a namespace of your own and you can't break anything shared.

The `web` Deployment comes from a manifest because it needs a readiness probe. `kubectl create deployment` adds none, and a pod with no readiness probe is Ready as soon as it runs, so it would stay 1/1 whatever the network did to probes, and the probe check at the end would prove nothing. The first few commands show the probe is live by switching podinfo's readiness off and on.

```bash
kubectl create namespace np-lab
kubectl -n np-lab apply -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata: {name: web}
spec:
  selector: {matchLabels: {app: web}}
  template:
    metadata: {labels: {app: web}}
    spec:
      containers:
      - name: podinfo
        image: ghcr.io/stefanprodan/podinfo:6.9.1
        ports: [{containerPort: 9898}]
        readinessProbe: {httpGet: {path: /readyz, port: 9898}, periodSeconds: 2}
EOF
kubectl -n np-lab expose deploy web --port=80 --target-port=9898
kubectl -n np-lab rollout status deploy/web
kubectl -n np-lab run client --image=curlimages/curl:8.11.1 --restart=Never --command -- sleep 3600
kubectl -n np-lab wait --for=condition=Ready pod/client
kubectl -n np-lab exec client -- curl -sS -m 5 -o /dev/null -w '%{http_code}\n' http://web    # 200

# The probe is live: fail it on purpose, then restore it.
kubectl -n np-lab exec deploy/web -- curl -sS -X POST -o /dev/null -w '%{http_code}\n' localhost:9898/readyz/disable   # 202
kubectl -n np-lab wait --for=condition=Ready=false pod -l app=web --timeout=60s   # condition met: 0/1
kubectl -n np-lab exec deploy/web -- curl -sS -X POST -o /dev/null -w '%{http_code}\n' localhost:9898/readyz/enable    # 202
kubectl -n np-lab wait --for=condition=Ready pod -l app=web --timeout=60s

# Out of the mesh, deny all egress: DNS goes first.
kubectl -n np-lab apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny-egress}
spec:
  podSelector: {}
  policyTypes: [Egress]
EOF
kubectl -n np-lab exec client -- curl -sS -m 5 http://web          # curl: (28) Resolving timed out after 5003 milliseconds
kubectl -n np-lab exec client -- curl -sS -m 20 http://web         # curl: (6) Could not resolve host: web, about 5 s later
kubectl -n np-lab delete netpol default-deny-egress

# Deny all ingress, then join the mesh, and watch the probes.
kubectl -n np-lab apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny-ingress}
spec:
  podSelector: {}
  policyTypes: [Ingress]
EOF
kubectl -n np-lab exec client -- curl -sS -m 5 http://web          # curl: (28) Connection timed out
kubectl label ns np-lab istio.io/dataplane-mode=ambient
kubectl -n np-lab rollout restart deploy/web
kubectl -n np-lab rollout status deploy/web --timeout=120s         # on tilt: rolled out, so the new pod passed its probe
kubectl -n np-lab get pods -l app=web                              # 1/1
kubectl -n np-lab delete netpol default-deny-ingress

# In the mesh, deny all egress again, from a new client pod.
kubectl -n np-lab apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny-egress}
spec:
  podSelector: {}
  policyTypes: [Egress]
EOF
kubectl -n np-lab run client2 --image=curlimages/curl:8.11.1 --restart=Never --command -- sleep 3600
kubectl -n np-lab wait --for=condition=Ready pod/client2
kubectl -n np-lab exec client2 -- curl -sS -m 5 http://web         # (28) Operation timed out ... with 0 bytes received: the name resolved
kubectl -n np-lab exec client2 -- curl -sS -m 5 http://nosuchsvc   # (28) Resolving timed out: ztunnel passed it on to CoreDNS
kubectl delete namespace np-lab
```

## What to remember

- A pod no policy selects is open. Select it and it is closed, except for what some policy allows, plus traffic from its own node.
- Out of a mesh, default deny for egress blocks DNS. Allow UDP and TCP 53 to kube-dns first.
- Both ends must allow a connection. Write the egress and the ingress.
- One list item with two selectors means both; two items mean either. Check with `kubectl describe`.
- In Istio's ambient mesh, allow port 15008 on both ends, expect Service names to keep resolving under a deny, and check what your plugin does to probes from 169.254.7.127.
