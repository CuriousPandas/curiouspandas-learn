The nightly report takes ten seconds to write. It runs as a **Job**: an object that starts a pod, waits for it to finish, and records the result as complete or failed ([a later lesson](/learn/kubernetes/jobs-and-cronjobs/) covers them in full). This Job has been running for forty minutes. The report container's logs say `report written`. The Job still says `0/1`, and the pod says `1/2 NotReady`.

This happened to enough people that it has a famous issue. In February 2019 someone wrote to the Istio project: "when the primary pod completes, the "Job" never completes because istio-proxy is still running". Istio had added a second container to every pod, and that container had no reason to stop.

## One pod, several containers

So far every pod here had one container. A pod can have more, sharing the pod's network and any volumes it mounts. There are three kinds, and the difference is all about *when they run* and *what waits for what*:

- **Regular containers** (`spec.containers`) are the app. The kubelet starts them one after another, in the order they're listed, without waiting for each to be ready, so in practice they come up together. The pod is finished when **all** of them have stopped.
- **Init containers** (`spec.initContainers`) run first, one at a time, and each must finish. The docs: "Init containers always run to completion. Each init container must complete successfully before the next one starts." Typical jobs: wait for a database, run a migration, download a file.
- **Sidecars** are helpers that run beside the app for its whole life: a log shipper, a proxy. Kubernetes now has a proper kind of sidecar, stable since v1.33 according to the docs: an init container with `restartPolicy: Always`. It starts before the app and is stopped *after* the app has finished.

The old way to add a sidecar was to put it in `spec.containers` as a second regular container. That's the trap in the opener. A Job is complete when its pod finishes; the pod finishes when every regular container has stopped; and a log shipper never stops. The docs describe the native kind's difference in one line:

> the sidecar container in each Pod does not prevent the Job from completing after the main container has finished.

## Find what's waiting

Two things are stuck. `nightly-report` has a regular sidecar. `shop` has an init container waiting for a database that isn't there. The files `report-plain.yaml` and `report-native.yaml` are in the sandbox's folder: `ls`, then `cat` them.

<KubeSim mission="kube-sidecars" title="Waiting for ever, two ways" />

<Callout kind="tip">
With more than one container, `kubectl logs <pod>` picks one and tells you so: `Defaulted container "app" out of: app, wait-for-db (init)`. Use `-c <name>` for the one you mean. An init container that's still running is the only one with anything to say: asking the app for logs gets `is waiting to start: PodInitializing`.
</Callout>

<Callout kind="trap">
You can't fix a Job's containers in place. Its pod template is fixed once the Job exists: `kubectl apply` of the changed file is refused with `spec.template: Invalid value: ...: field is immutable` (on a real cluster, a very long line). Delete the Job and create it again. (One narrow exception, from the v1.36 source: a Job that is suspended and has never started may still change scheduling fields such as its node selector and tolerations, but not its containers.)
</Callout>

## Reading the status column

| STATUS | What it means |
|---|---|
| `Init:0/1` | The first of one init container is running and hasn't finished |
| `Init:Error`, then `Init:CrashLoopBackOff` | An init container exited with an error; the kubelet restarts it, waiting longer each time |
| `PodInitializing` | Init containers are done; the app container is being started |
| `NotReady` | One regular container has finished and another is still running, so the pod isn't Ready: the app finished and a regular sidecar didn't |
| `Completed` | Every regular container exited with 0 |

A pod whose container is running but failing its readiness check doesn't say `NotReady`: it says `Running`, with `0/1` in READY. The READY column counts regular containers and native sidecars: `1/2` on the stuck report pod means the shipper is up and the report container, which has finished, is not.

<Callout kind="real">
Three simplifications. The sandbox's `wait-for-db` image waits until a Ready pod labelled `app=db` exists in its namespace; a real one would loop on a DNS lookup or a TCP connection to a Service, which this sandbox doesn't model. Real containers in a pod also share an `emptyDir` volume when you give them one: a scratch folder that lives exactly as long as the pod, the usual way an init container hands a file to the app. The sandbox lets you mount one but keeps no files in it. And on a real cluster the native sidecar Job took about 42 seconds, not 10: the busybox log shipper ignored the stop signal, so the kubelet waited out its 30-second grace period and killed it (exit code 137) before the pod counted as finished. The sandbox's log shipper does the same, and shows the same sequence a real cluster did on kind v1.36.1: `0/2 Init:0/1`, then `2/2 Running`, then `1/2 Completed` with the pod still in phase Running for the grace period, then `0/2 Completed`. Its timings are coarser, because the sandbox moves in 5-second ticks.
</Callout>

## What to remember

- Init containers run first, in order, and must finish. A stuck one leaves the app with no logs: use `-c`.
- A regular second container keeps a pod, and so a Job, alive for ever. A native sidecar is an init container with `restartPolicy: Always`.
- A Job's pod template can't be edited. Delete and recreate.

<DoItForReal id="kube-init-real">

On the tilt platform, in a scratch namespace. Run on 2026-11-03 against Kubernetes v1.36.1: within a minute the native Job was `Complete` (duration 42 s) and the plain one sat at `0/1`, its pod `1/2 NotReady`.

```bash
kubectl create namespace sidecar-lab
kubectl -n sidecar-lab apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata: {name: plain-sidecar}
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: report
        image: busybox:1.36
        command: [sh, -c, 'echo writing report; sleep 5; echo report written']
      - name: log-shipper
        image: busybox:1.36
        command: [sh, -c, 'while true; do echo shipping; sleep 5; done']
---
apiVersion: batch/v1
kind: Job
metadata: {name: native-sidecar}
spec:
  template:
    spec:
      restartPolicy: Never
      initContainers:
      - name: log-shipper
        image: busybox:1.36
        restartPolicy: Always
        command: [sh, -c, 'while true; do echo shipping; sleep 5; done']
      containers:
      - name: report
        image: busybox:1.36
        command: [sh, -c, 'echo writing report; sleep 5; echo report written']
EOF
kubectl -n sidecar-lab get jobs,pods          # run again after a minute
kubectl -n sidecar-lab get pod -l job-name=plain-sidecar -o jsonpath='{.items[0].status.containerStatuses[*].state}'
kubectl delete namespace sidecar-lab
```

Then look at a pod on the platform's mesh: `kubectl -n hello get pod -o jsonpath='{.items[0].spec.containers[*].name}'` prints only `podinfo`. The tilt platform runs Istio in ambient mode, which puts no proxy container in your pods at all, so this whole problem doesn't arise there. [The service mesh lesson](/learn/platform/service-mesh/) explains what ambient mode does instead.
