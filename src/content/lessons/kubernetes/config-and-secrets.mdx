The shop's web app greets visitors with a line of text kept in a **ConfigMap**, not baked into the image. Marketing wants it changed. You edit the ConfigMap, Kubernetes says `configmap/greeting patched`, and the site keeps saying the old thing. An hour later it still does. No error anywhere.

Nothing failed. The app read its configuration once, when it started, and it hasn't started since.

## ConfigMaps and Secrets

A **ConfigMap** is a stored object that holds `key: value` pairs of configuration: a greeting, a feature flag, a whole config file. A **Secret** is the same idea for things that must not be shown around, like a database password. Keeping them outside the image means one image can run in test and production with different settings.

A pod can use them in two ways:

1. As **environment variables**, set when the container starts. The app reads `$GREETING` like any other variable.
2. As **files**, by mounting the ConfigMap as a volume: each key becomes a file in a folder inside the container.

Those two behave differently when the ConfigMap changes, and the docs spell out both:

> ConfigMaps consumed as environment variables are not updated automatically and require a pod restart.

For mounted files, the kubelet (the agent on each node that runs containers) refreshes them on its own schedule, so the delay "can be as long as the kubelet sync period + cache propagation delay". With the default settings that's typically up to a minute and a half: the kubelet comes back to each pod every minute plus a random extra of up to half that again (a jitter factor of 0.5 in the kubelet's pod workers, Kubernetes v1.36 source). Over five changes on kind v1.36.1 clusters, the new value took between 56 and 78 seconds to appear in the file. And one more case the docs single out:

> A container using a ConfigMap as a subPath volume mount will not receive ConfigMap updates.

A **subPath** mount places one key as one file at a path you choose, instead of mounting the whole folder. It's popular for dropping a single config file into a directory that already has other files in it. The container gets the file as it was when the container started, and it stays that way.

## See it, then fix it

`web` reads `GREETING` from its environment. `api` needs a database password it doesn't have. Change the greeting, find out whether `web` noticed, make it notice, then give `api` its password the right way.

<KubeSim mission="kube-config" title="Config that stays put" />

<Callout kind="trap">
`kubectl set env deployment/web --from=configmap/greeting` doesn't link the Deployment to the ConfigMap. It reads the ConfigMap *now* and writes one environment entry per key it finds, each pointing at that key. Restarting picks up a changed **value**. A key added to the ConfigMap later never arrives, however often you restart: on a real cluster the Deployment's YAML shows `valueFrom.configMapKeyRef` entries, one per key, and no `envFrom`.
</Callout>

## Mounted files change by themselves

Now the other kind of mount. `files` mounts the same ConfigMap twice: once as a folder at `/etc/greeting`, and once as a single subPath file at `/etc/sub/GREETING`. Change the greeting and keep watching. Time runs on its own here, about 5 seconds of cluster time per tick.

<KubeSim mission="kube-config-volume" title="The folder and the single file" />

<Callout kind="real">
The sandbox refreshes every mounted folder exactly 60 seconds after its volumes were mounted, and every 60 seconds after that, and it notices nothing else. A real kubelet's delay depends on its sync period and cache settings, so the gap varies from seconds to about a minute and a half. Neither tells the app: a real program has to re-read its file, or watch it, to pick the change up. Many don't, which is why a restart is still the usual way to roll out new config.
</Callout>

## Secrets are base64, not encrypted

In `kubectl get secret db -o yaml` the password appears as a string like `cG9zdGdyZXM6Ly9...`. That's **base64**, a way of writing any bytes using only letters, digits, `+` and `/`, with `=` on the end as padding. It's an encoding, not a lock: anyone can turn it back with `base64 -d`, and no key is involved. The docs' own warning is blunter:

> Kubernetes Secrets are, by default, stored unencrypted in the API server's underlying data store (etcd).

By default a Secret is stored no more safely than a ConfigMap. The differences are in who may read it and how it's handled: the built-in `view` role can read ConfigMaps but not Secrets, the kubelet keeps a Secret's mounted files in memory (`tmpfs`) rather than on the node's disk, and a cluster can be set up to encrypt Secrets in etcd. `kubectl describe secret` shows only sizes (`DATABASE_URL:  23 bytes`) so the value doesn't land on a screen by accident, but the permission to *get* the Secret is the permission to read it. Who gets that permission is the subject of [the cluster-access lesson](/learn/security/cluster-access/), and why a Secret's YAML must never go into git is [the secrets-in-git lesson](/learn/security/secrets-in-git/).

## What to remember

- Environment variables are read once, at container start. Change the ConfigMap, then restart the pods.
- Mounted folders refresh on the kubelet's schedule, typically within a minute and a half. subPath files never do.
- `set env --from=configmap/x` copies today's keys. New keys need the command again.
- base64 is not encryption. A Secret is only as private as the permission to read it.

<DoItForReal id="kube-config-real">

On the tilt platform, in a scratch namespace you delete at the end. These steps were run on 2026-11-03 against Kubernetes v1.36.1.

```bash
kubectl create namespace config-lab
kubectl -n config-lab create configmap greeting --from-literal=GREETING=v1
kubectl -n config-lab create deployment web --image=busybox:1.36 -- \
  sh -c 'while true; do echo "GREETING=$GREETING"; sleep 5; done'
kubectl -n config-lab set env deployment/web --from=configmap/greeting
kubectl -n config-lab rollout status deployment/web
kubectl -n config-lab get pods                 # wait until only one web pod is left
kubectl -n config-lab logs deploy/web --tail=1 # GREETING=v1
kubectl -n config-lab patch configmap greeting -p '{"data":{"GREETING":"v2"}}'
kubectl -n config-lab logs deploy/web --tail=1 # still GREETING=v1
kubectl -n config-lab rollout restart deployment/web
kubectl -n config-lab rollout status deployment/web
kubectl -n config-lab get pods                 # again, wait for the old pod to go
kubectl -n config-lab logs deploy/web --tail=1 # GREETING=v2
kubectl -n config-lab create secret generic db --from-literal=DATABASE_URL=postgres://db:5432/shop
kubectl -n config-lab get secret db -o jsonpath='{.data.DATABASE_URL}' | base64 -d; echo
kubectl delete namespace config-lab
```

Why the waiting: this busybox loop ignores the polite stop signal, so an old pod lingers for its 30-second grace period after the rollout says it's done. While it does, `kubectl logs deploy/web` prints `Found 2 pods, using pod/...` and may pick the old one. When this was run, it did, and showed the old value.

</DoItForReal>
