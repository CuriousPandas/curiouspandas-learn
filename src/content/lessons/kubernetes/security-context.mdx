A security review asks for one change: don't run containers as root. You add `runAsNonRoot: true` to the Deployment. The new pod never starts. `kubectl logs` says the container "is waiting to start: CreateContainerConfigError". There is nothing else to read, because the program never ran.

The pod's events have the reason, word for word from a real kind v1.36.1 cluster running the stock `nginx` image:

```text
Error: container has runAsNonRoot and image will run as root (pod: "nginx_sec(06f4...)", container: nginx)
```

## What a securityContext is

A **securityContext** is a block of settings in a pod or container spec that controls what the process is allowed to be and do. A few you'll meet constantly:

- `runAsUser`: the numeric user id the process runs as. 0 is root.
- `runAsNonRoot: true`: a check, not a change. The kubelet refuses to start the container if it would run as user 0.
- `allowPrivilegeEscalation: false`: the process can't gain more rights than it started with, for example through a setuid program.
- `capabilities.drop: ["ALL"]`: Linux splits root's powers into pieces called **capabilities** (binding low ports, changing file owners, and so on). Dropping all of them leaves an ordinary process.
- `readOnlyRootFilesystem: true`: the container's own files can't be changed. Anything the app writes needs a mounted volume.
- `seccompProfile`: a filter on which system calls the process may make. `RuntimeDefault` uses the container runtime's standard filter.

Settings on the pod apply to every container; settings on a container override them.

## Why it refused

`runAsNonRoot` doesn't make anything non-root. It asks the kubelet to check. The image's own metadata says which user it runs as, and many, the official `nginx` image included, say root. So the check fails before the program starts, and the pod sits in **CreateContainerConfigError** for ever. The fix is to say which non-root user to run as (`runAsUser: 1000`), or to use an image built to run as one.

Setting `runAsUser: 0` alongside `runAsNonRoot: true` gets a different message from the same check: `container's runAsUser breaks non-root policy`.

## Two gates

Then there's a second, wider gate. **Pod Security admission** is built into the API server and checks every new pod in a namespace against one of three published levels: `privileged` (anything goes), `baseline` (blocks the known ways out, such as privileged containers) and `restricted` (the hardened settings above). You choose by labelling the namespace, in one of three modes. The docs:

> enforce Policy violations will cause the pod to be rejected.

> warn Policy violations will trigger a user-facing warning, but are otherwise allowed.

> audit Policy violations will trigger the addition of an audit annotation to the event recorded in the audit log, but are otherwise allowed.

<KubeSim mission="kube-nonroot" title="The kubelet's check, then the API server's" />

<Callout kind="trap">
A namespace labelled only `pod-security.kubernetes.io/audit=restricted` or `warn=restricted` admits every pod. On a real cluster a non-compliant `kubectl run` in such a namespace printed `Warning: would violate PodSecurity "restricted:latest": ...` and then `pod/y created`. Audit and warn modes show you what *would* break before you switch to enforce. They are not protection.
</Callout>

<Callout kind="trap">
Switching enforcement on doesn't touch pods that are already running. The API server lists them as warnings when you add the label (`Warning: existing pods in namespace ... violate the new PodSecurity enforce level`) and leaves them be. The next time one of them is replaced, by a crash, a node drain or a rollout, its replacement is refused. A namespace can look compliant for weeks and fail on the first restart.
</Callout>

<Callout kind="real">
The sandbox's images declare their user the way a Dockerfile's `USER` line does: `panda/hello` runs as root, `panda/hello-nonroot` as 1000. It models only these Pod Security checks: privileged and added capabilities at baseline, and at restricted also privilege escalation, dropping all capabilities, runAsNonRoot, runAsUser 0 and seccomp. The real levels check more, such as host namespaces, host paths and volume types. Its `readOnlyRootFilesystem` effect is simplified too: the sample apps write only to `/tmp`, and a real app may need several folders.
</Callout>

## Sometimes root is the job

Not every pod can be restricted. The tilt platform runs a DaemonSet called `istio-ambient-node-prep` with `privileged: true` and `hostPID: true`, which baseline forbids. Its comment says why: "kind nodes start with /run private. istio-cni needs it rshared to enter pod netns; without this ambient capture silently no-ops." It changes how the node itself mounts a folder, which no ordinary container may do. The honest pattern is to keep such things in a namespace of their own, labelled `privileged`, with a comment saying why, and keep application namespaces restricted.

## What to remember

- `runAsNonRoot` is a check against the image's user. Pair it with `runAsUser`, or an image that sets `USER`.
- The kubelet's checks leave a stuck pod with events. Pod Security leaves no pod, only a FailedCreate event.
- Only `enforce` refuses. `warn` and `audit` let everything in.
- Turning enforcement on spares running pods until they're replaced.

<DoItForReal id="kube-sec-real">

On the tilt platform, in a scratch namespace. Run on 2026-11-03 against Kubernetes v1.36.1; the messages were exactly the ones in this lesson.

```bash
kubectl create namespace sec-lab
kubectl -n sec-lab run nginx --image=nginx:1.27 \
  --overrides='{"spec":{"securityContext":{"runAsNonRoot":true}}}'
kubectl -n sec-lab get pod nginx                 # CreateContainerConfigError
kubectl -n sec-lab describe pod nginx | tail -5
kubectl label ns sec-lab pod-security.kubernetes.io/enforce=restricted   # read the warning
kubectl -n sec-lab run x --image=nginx:1.27      # Forbidden: violates PodSecurity "restricted:latest"
kubectl -n istio-system get ds istio-ambient-node-prep \
  -o jsonpath='{.spec.template.spec.containers[0].securityContext}{"\n"}{.spec.template.spec.hostPID}{"\n"}'
kubectl delete namespace sec-lab
```
