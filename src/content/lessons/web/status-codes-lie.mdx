Here's a health check that ships every day, all over the world:

```bash
curl https://shop.bamboo.example/ && echo "site is up"
```

It prints "site is up" when the site returns `500 Internal Server Error`. **By default, curl doesn't treat an HTTP error status as a failure.** It got an answer, so it exits 0. The manual says so in as many words. You have to add `--fail` to get exit code 22 on a 4xx or 5xx.

So you fix the check to look at the status code. Now it catches the 500, and it waves through something worse: a `200 OK` whose page is an empty shell. Modern sites send a skeleton page and a script that fills it in. If that script fails, or the data request behind it fails, the server still says 200, and the visitor sees a blank screen.

<Callout kind="trap" title="The shape of the bug">
Every check above is *configured*. It runs, it reports green, and it checks nothing that matters. A check that can't fail is worse than having no check, because it reads as proof.
</Callout>

## Three checks, ten ways to fail

Try each failure and watch the scoreboard. A check is **fooled** when it says "fine" about a broken site, or "broken" about a fine one.

<RequestJourney start="shell" title="Would your health check notice?" />

Only one check is right every time: **does the body contain something that only a working page would contain?** Not "is the body non-empty": the empty shell isn't empty. Look for the shop's name, a product, a value you know should be there. For a page that builds itself in the browser, the honest version is to render it in a real browser and read what's on screen, which is exactly how this site checks its own pages.

## 401 vs. connection reset

Two failures look the same in a test log: "request failed". They mean opposite things.

- A **401** is an answer from the application. Your request crossed the network, got through TLS, reached the code, was read, and was refused for lack of credentials. Whatever is guarding that door is working.
- A **connection reset** (curl exit 56) means something on the path tore the connection down. The application may never have seen your request. If you were testing that a firewall blocks you, a reset might be the firewall doing its job. If you were testing the application's own login check, the reset proves nothing about it.

When you test that something is refused, check **how** it was refused. "It failed" isn't evidence. "It failed at the layer I meant to test" is.

<DoItForReal id="web-lie-real" lab="08-empty-dashboard" profile="observability">

Make curl lie, then make it honest:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://hello.localhost/nope ; echo "exit=$?"
curl -sf -o /dev/null https://hello.localhost/nope ; echo "exit=$?"
curl -s https://hello.localhost/ | grep -q "Hello from the platform" && echo "really up"
```

The hello app is podinfo. Its message, "Hello from the platform", is set in `examples/hello-world/deployment.yaml`, so that string is something only a working page contains.

The platform's own `./scripts/platform.sh check` does it properly: it renders every service in a real browser and reads the screen.

</DoItForReal>
