You type `shop.bamboo.example` and press Enter. Before a single pixel of the shop shows up, your computer has to get through four separate stages, in order. Each can fail on its own, and each fails in its own way:

1. **DNS** turns the name into an address. Computers route packets to numbers like `203.0.113.10`, not names, so your machine asks a DNS resolver, which may ask other servers, and caches the answer for a while.
2. **TCP** opens a connection to that address and port. Three messages go back and forth (SYN, SYN+ACK, ACK) before either side sends any real data. RFC 9293 calls it the three-way handshake.
3. **TLS** proves you're talking to the real `shop.bamboo.example` and encrypts everything after. The server shows a certificate; your machine checks the name on it and who signed it.
4. **HTTP** finally asks for the page (`GET /`) and gets an answer: a status code, some headers and a body.

The useful skill isn't memorising the stages. It's reading **where** a request died from **how** it died. A failed DNS lookup and a crashed server both mean "the site is down", but one is a typo in a record and the other is a 3 a.m. phone call.

## Break it

Pick a failure. The stage tracker shows how far the request got, and the terminal shows what `curl -v` actually prints. The exit codes and messages are real curl output, captured for this lesson.

<Callout kind="tip">
Notice the *speed* of each failure. "Connection refused" comes back in milliseconds: a machine answered to say nothing is listening. A timeout takes as long as you're willing to wait: nothing answered at all. Fast-no and slow-silence point at different culprits.
</Callout>

<Callout kind="real">
Browsers and servers are moving to **HTTP/3**, which runs over QUIC on UDP and folds the TCP and TLS stages into one handshake. The stages blur together, but the questions don't change: did the name resolve, did anything answer, did it prove who it is, and what did it say?
</Callout>

<DoItForReal id="web-journey-real" lab="02-route-a-hostname">

With the tilt platform up, watch all four stages against a real service:

```bash
curl -v https://hello.localhost/
curl -v https://no-such-name.invalid/       # stage 1 fails: exit 6
curl -v http://127.0.0.1:9/                 # stage 2 fails: exit 7
echo $?                                     # the exit code of the last command
```

Names ending in `.localhost` point at your own machine (RFC 6761), and that's how the platform gets real hostnames with no DNS setup. Lab 02 then has you route a second hostname.
