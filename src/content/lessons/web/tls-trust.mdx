During the TLS stage the server hands over a **certificate**. It says, roughly, "I am `shop.bamboo.example`, and *Bamboo Root CA* vouches for me." Your machine checks two separate things:

1. **The name.** Does the certificate list the name you asked for? Certificates carry their names in a field called the Subject Alternative Name (SAN).
2. **The trust.** Can it follow the chain of signatures up to a root certificate that your machine already trusts? Your operating system and browser ship with a list of trusted roots, the **trust store**.

Fail either one and you get the same scary browser page and the same curl exit code: **60**. That sameness is the trap. The two failures have opposite fixes, and fixing the wrong one wastes an afternoon.

## Same symptom, different code

OpenSSL's `s_client` does tell them apart, with a numbered verify code:

| Verify code | Meaning | Fix |
|---|---|---|
| **62** hostname mismatch | the chain is trusted; the name isn't on the certificate | edit the **certificate**: add the name |
| **20** unable to get local issuer certificate | the name is right; nothing you trust signed it | fix the **trust store** (or the chain the server sends) |

Codes 18 to 21 are the family of trust failures. 18, for example, is a self-signed certificate. The rule from tilt lab 04 is short: **62 means go edit the certificate; 18 to 21 mean go fix the trust store.**

<Callout kind="trap" title="The fix that isn't">
`curl -k` and "proceed anyway" make both errors go away by switching off the check. That doesn't fix anything. It removes the only thing telling you whether you're talking to the real server. If it ends up in a script, it stays there.
</Callout>

<Callout kind="real">
The playground shows certificates as one tidy line each. Real chains usually have an **intermediate** certificate between the server and the root, and a server that forgets to send it produces code 20 on some clients and not others, depending on what each client has cached. Also, in TLS 1.3 the certificate itself is encrypted on the wire, so you inspect it with `openssl s_client` or the browser's padlock, not by sniffing packets.
</Callout>
