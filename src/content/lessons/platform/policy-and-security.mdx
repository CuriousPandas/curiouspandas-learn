Security in a cluster isn't one tool. It's a question asked at three different moments, and the tilt platform has a tool for each:

| When | Question | Tool on the platform |
|---|---|---|
| **Before it runs** (admission) | Should this pod be allowed in at all? | **Kyverno**: policies written as Kubernetes resources that validate, mutate or generate objects |
| **What's inside** (scanning) | Does this image contain known-vulnerable packages? | **Trivy Operator**: scans running workloads' images and writes the results as reports in the cluster |
| **While it runs** (runtime) | Is this container doing something it never should, like starting a shell or reading secrets? | **Falco**: watches what processes actually do at the system-call level and raises alerts |

They overlap on purpose. A policy can't catch a vulnerability in a library, a scanner can't catch an attacker using a perfectly patched shell, and runtime detection only fires after something has already happened.

## The policy that protects nothing

The platform ships twelve Kyverno policies adapted from Kyverno's Pod Security Standards library, such as *disallow privileged containers* and *disallow host paths*. Its own README opens with this:

> Every one is in `audit` mode, so none of them blocks anything.

In **audit** mode a violating pod is admitted, a `PolicyReport` is written, and the pod runs. In **enforce** mode it's refused at admission, like the quota in the Kubernetes track. Audit is deliberate here: the mesh's ztunnel and the log collectors genuinely need privileged access and host paths, so enforcing everything would break the platform itself.

The lesson isn't that audit is wrong. It's that **a policy that reports and never refuses looks exactly like a policy that protects you**, unless you check which one you have:

```bash
kubectl get clusterpolicy -o custom-columns='NAME:.metadata.name,ACTION:.spec.validationFailureAction'
```

<Callout kind="real">
Turning on a single policy is the useful experiment. The platform's README suggests enforcing just `disallow-privileged-containers` and restarting ztunnel: the refusal names the policy and the rule. Then put it back to `Audit` before the mesh notices.
</Callout>

<DoItForReal id="platform-sec-real">

All three are off by default. Turn them on in `tilt-config.json`, under `flux_apps`, with Tilt running. It notices the file change and deploys them:

```json
"kyverno": { "enabled": true },
"trivy":   { "enabled": true },
"falco":   { "enabled": true }
```

```bash
kubectl get clusterpolicy -o custom-columns='NAME:.metadata.name,ACTION:.spec.validationFailureAction'
kubectl get policyreport -A
kubectl get vulnerabilityreports -A | head
kubectl -n falco logs -l app.kubernetes.io/name=falco --tail=20
```

The Kyverno README in `helm/kyverno-policies/` explains each policy and which platform components would violate them. It says plainly that the list is reasoned, not measured.

</DoItForReal>
