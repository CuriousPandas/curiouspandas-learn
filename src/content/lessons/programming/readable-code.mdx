In the Sixth Edition of Unix, from around 1975, the part of the system that switches between running programs had a comment that became famous: `You are not expected to understand this.`

Dennis Ritchie, one of Unix's authors, later explained it on his own web page. It "was intended as a remark in the spirit of 'This won't be on the exam,' rather than as an impudent challenge." And then he gave the real reason: "The real problem is that we didn't understand what was going on either."

The mechanism only worked because of how one compiler happened to behave. When he and Steve Johnson moved Unix to a different machine, it stopped working, and he writes: "It took about a week of agonizing before we finally convinced each other that the mechanism was wrong".

If that can happen to the people who wrote Unix, it can happen to you with something you wrote last month. The person who most often has to read your code is you, later, having forgotten everything. PEP 8, Python's style guide, starts from the same idea: "code is read much more often than it is written".

## Try reading both

This is the core of the lesson, and it doesn't need anyone's authority. Here is one function, written twice. Cover the second and try to work out what the first does. Time yourself if you like.

```python
def f(d, r):
    x = r - d
    if x <= 0:
        return 0
    if x > 30:
        return 30 * 25 + (x - 30) * 50
    return x * 25

print(f(10, 15))
```

```python
FIRST_DAYS = 30
FIRST_RATE = 25    # cents a day
LATER_RATE = 50    # doubled, so that books come back before anyone needs them

def days_late(due_day, returned_day):
    return max(0, returned_day - due_day)

def late_fee(due_day, returned_day):
    days = days_late(due_day, returned_day)
    if days <= FIRST_DAYS:
        return days * FIRST_RATE
    return FIRST_DAYS * FIRST_RATE + (days - FIRST_DAYS) * LATER_RATE

print(late_fee(due_day=10, returned_day=15))
```

Both print 125. The computer doesn't care which you pick: they give the same answer, and this site's tests compare them across hundreds of inputs. The differences are all for the person reading:

- **Names say what a thing is.** `d` means nothing until you've read the rest. `due_day` means something on its own.
- **A small function names an idea.** `days_late` is a sentence you can skip once you trust it, and a piece you can test on its own.
- **A named number has one home.** Is that `30` the same 30 as the other one? In the first version you have to work it out, and in the second you can see that it is.

The second version isn't free. It's longer, and you have to look in two places to follow it. For a three-line helper you'll read once, a short version can be better. Python's own guide warns against following a style rule blindly, under the heading "A Foolish Consistency is the Hobgoblin of Little Minds". You're making a judgement about a reader, not obeying a law.

## What the research says, and doesn't

You'll hear confident rules about readability, often with "studies show". We went and read what we could. The honest summary is that the evidence is thin, conflicting, and much smaller than the confidence.

| Question | What was found |
|---|---|
| Do full-word names beat abbreviations? | Greg Wilson's 2021 review of three 2017 studies says they conflict. Scanniello and others found no difference in effort or efficiency. Beniamini and others found no difference in comprehension for single-letter names. Hofmeister and others found words did better than letters and abbreviations, by 19%. He concludes the issue "probably falls under the heading of 'not worth worrying about'". |
| Do longer, descriptive names help? | Schankin and others (88 Java developers, 2018) found people located a logic defect about 14% faster with descriptive names. That disappeared when they hunted a syntax error, and it showed for the more experienced developers and not the less experienced. |
| `camelCase` or `under_score`? | Binkley and others (135 programmers and non-programmers, 2009) found camel case more accurate and, overall, about 13.5% slower. Sharif and Maletic set out to repeat that with an eye tracker (2010), and found no difference in accuracy and quicker recognition of underscores. A big difference between the two: which style people were trained in. |
| Do developers agree on names? | Feitelson and others (a sequence of experiments with 334 people in total): in the first, the probability that two developers pick the same name had a median of only 6.9%. Though once a name was chosen, most developers understood it. |

The caveats go further. Most of these are short exercises on small snippets, and a timed puzzle isn't the same as living with a codebase for years. We read the abstracts and Wilson's review for these studies, not every paper in full, so read them yourself before you quote them at anybody.

We also went looking for good evidence behind the common advice that a function should be no longer than some number of lines. We didn't find a study we'd stand behind, so we won't give you a number. Treat "keep them small" as a craft habit, not a finding.

That leaves less than the confident rules suggest. So here's our opinion, marked as opinion: a misleading name is worse than a short one, and your own experience of reading both versions above is decent evidence about you. Use it.

## Comments: say why

The first version's problem isn't only a lack of comments. Adding `# subtract d from r` above `x = r - d` tells you nothing the code doesn't. Good comments say what the code can't:

- **Why** this way and not the obvious way.
- **What goes wrong** if someone removes this line.
- **What was left out on purpose,** because something missing looks like an oversight.

Even so, a comment isn't checked by anything. It can be wrong for years. Run this, then decide which of the comment and the code is telling the truth.

<CodeLab code={`def shipping(total):
    # Free delivery on orders over 50.
    if total > 40:
        return 0
    return 5

print(shipping(45))
`} />

You can't tell from here. Either the comment is out of date, or the code has a bug, and only someone who knows the business can say. PEP 8 is blunt about it: "Comments that contradict the code are worse than no comments." When you change the code, change its comment. If a comment only repeats the code, delete it, and that's one less thing to go stale.

A function can also describe itself. Python's convention for this is a **docstring**: a string on the first line of the function saying what it does for its caller, and what it expects. `help()` in real Python displays it.

```python
def days_late(due_day, returned_day):
    """How many days overdue, and never below 0. Days are plain day numbers."""
    return max(0, returned_day - due_day)

print(days_late(10, 15))
```

## What to remember

- Code is read far more than it's written, usually by you, later.
- Good names and small functions are for the reader. Read both versions and judge.
- The research on readability is real, thin and contested. Be suspicious of "studies show" without a study.
- Comments say why. If one only says what, delete it. If it contradicts the code, something is wrong.
- One idea should live in one place, so a change is one edit.
