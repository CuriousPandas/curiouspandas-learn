On 9 September 1947, the team running the Harvard Mark II found a moth trapped in one of its relays. They taped it into the logbook and someone wrote: "First actual case of bug being found." Grace Hopper was there and, as the Computer History Museum puts it, "made the incident famous later on in her many public lectures".

It's a good story, and it's often told wrong. It isn't where the word came from: the same museum page traces "bug" to Thomas Edison in the 1800s, and the note only works as a joke if the word already existed. And the museum says Hopper was present, not that she found it. The log is still a fine lesson, though. Somebody found the exact place the machine was failing, and wrote down what they found.

Your bugs won't have wings, and they come in three kinds. Each needs a different approach:

- **It crashes.** You get a report. Start there.
- **It gives a wrong answer and no error.** Nothing tells you where to look, so you have to watch it run.
- **It works when you try it, and fails for someone else.** You have a guess to test, and the input to find.

## Read the report from the bottom up

When an exception reaches the top, Python prints a **traceback**: the trail of function calls that were waiting when things went wrong. This one comes from the program in the lab below.

```text
Traceback (most recent call last):
  File "<lab>", line 18, in <module>
    print(report(["tea,2.50", "cake,4.00"]))
  File "<lab>", line 16, in report
    return total(prices)
  File "<lab>", line 9, in total
    t = t + p
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

Beginners read this from the top, get lost in the noise, and give up. Read it from the **bottom**:

1. **The last line says what went wrong.** You tried to add an `int` and a `str`. So one of those values isn't what you assumed.
2. **The line above it says where.** Line 9, inside `total`: `t = t + p`.
3. **Going up the list shows how you got there.** `total` was called from line 16 in `report`, which was called from line 18, the top of the program. "Most recent call last" means the newest call is at the bottom.

Then you ask the real question: not "what's wrong with line 9?", but "how did a `str` get here?" A traceback tells you where it hurt. It doesn't tell you where the mistake is, and on this next one those are different places.

## No error, wrong answer: use Step

A program with no crash gives you no report. Printing values is one way in, and it's a good one. The other is a **debugger**, a tool that runs your program one line at a time and shows you every variable as you go. In these labs that's the **Step** button.

The way to use it is not to watch passively. **Before each press, say what you expect to happen.** The bug is on the first line where your expectation and the program disagree. If you only watch, your eye slides over the moment it goes wrong.

## Test a guess, don't just change things

The tempting way to debug is to change something, run it, and change something else until it works. That can make the symptom go away and leave you with a program you understand less than before, with no way of knowing whether the bug has really gone.

The reliable way is the one scientists use:

1. **Observe.** What exactly happens, and on what input? Find the smallest input that shows it.
2. **Guess.** Say why, specifically. "It's broken" isn't a guess. "Removing an item makes the loop skip the next one" is.
3. **Predict.** If your guess is right, what else must be true? Name something you haven't seen yet.
4. **Test.** Run that one thing. If the prediction fails, the guess was wrong, and you've learned something for the cost of one run.
5. **Then fix,** and check that the original failure is gone.

Change one thing at a time. If you change three things and it starts working, you don't know which one did it, or whether the other two broke something else.

This sandbox has **Step** and no breakpoints. On a real machine, Python comes with a debugger called `pdb`: put `breakpoint()` on a line and the program stops there and lets you look around. On a real machine with Python 3, save this as `bug.py`:

```python
# real machine
def longest_run(items):
    best = 0
    current = 0
    previous = None
    for x in items:
        breakpoint()
        if x == previous:
            current += 1
        else:
            current = 1
        best = max(best, current)
        previous = x
    return best

print(longest_run(["a", "a", "b"]))
```

Run `python3 bug.py`. At the `(Pdb)` prompt, type `p current` to print a value, `n` for the next line, `c` to carry on to the next stop, and `q` to quit. Quitting prints a traceback ending in `bdb.BdbQuit`. That's normal: it's `pdb` stopping your program, and not a new bug. Python's docs list the rest.

</DoItForReal>

## What to remember

- Read a traceback from the bottom: what went wrong, where, then how it got there.
- Where it crashed and where it's wrong are often two different places.
- With no error, step through it, and say what you expect before each step.
- A guess you can test beats a change you hope will work.
- A fix isn't done until it works on inputs you weren't looking at.
