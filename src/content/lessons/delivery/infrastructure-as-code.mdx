Clicking through a cloud console works once. The second time, nobody remembers which boxes were ticked, and the third environment is a little different from the first two. **Infrastructure as code** writes the infrastructure down in files instead, and a tool - Terraform, OpenTofu, Pulumi, Crossplane - makes reality match them.

The tool keeps three things apart, and every surprise in this lesson lives in the gaps between them:

- **The configuration** - what you wrote.
- **The state** - what the tool remembers creating, as of its last apply.
- **The cloud** - what actually exists right now.

## Reading a plan

The OpenTofu docs describe what a plan does in three steps: it reads the current state of the real objects, compares the configuration with what it knows, and proposes the changes that would make them match. A plan is safe to run as often as you like. It's the review.

Each proposed change carries a symbol, and the symbols are the whole skill:

| Symbol | Meaning | Ask yourself |
|---|---|---|
| `+` | create | is this new thing meant to exist? |
| `~` | update in-place | the object stays; one setting changes |
| `-/+` | replace: destroy, then create | what was on the old one, and what points at it? |
| `-` | destroy | is anything in there you need? |

A **replace** is the one people miss. Some settings can't be changed on a live object - HashiCorp's docs put it as arguments that cannot be updated in-place due to remote API limitations - so the tool destroys the object and creates a new one. A new server gets a new address, and everything pointing at the old one has to change in the same plan.

Drift doesn't always announce itself. Edit a file managed by Terraform's `local_file` resource by hand, and the next plan (checked with Terraform 1.16.3) doesn't report a change made outside Terraform. It reports the resource as simply **will be created**, because that provider treats a changed file as gone. How drift shows up depends on the provider, so read every plan line, not just the summary.

## Drift is a symptom

HashiCorp's drift tutorial says it directly: you should not make manual changes to resources a tool controls, because the state drifts from the real infrastructure. The next plan will quietly put your code back - undoing a 3am console fix that was holding something up. When you must change things by hand, write the change into the code straight afterwards. Then the plan agrees with you.

This is the same idea as [Git as the source of truth](/learn/platform/gitops/), where a controller re-applies the repository on a timer instead of waiting for someone to run a plan.

These are real lines from a Terraform 1.16.3 plan after changing a field that can't be updated in place - here the content of a `local_file`, a resource that only writes a file on your disk, so no cloud account is needed:

```text
Resource actions are indicated with the following symbols:
-/+ destroy and then create replacement
  # local_file.greeting must be replaced
      ~ content              = <<-EOT # forces replacement
Plan: 1 to add, 0 to change, 1 to destroy.
```

<DoItForReal id="delivery-iac-real" lab="01-deploy-a-service">

Kubernetes manifests are infrastructure as code too, and `kubectl diff` is their plan: it exits 0 when nothing differs and 1 when something does. On the running platform, after lab 01:

```bash
kubectl diff -k examples/hello-world; echo "exit $?"     # 0: live matches the files
kubectl -n hello scale deploy/hello --replicas=3        # the console click
kubectl diff -k examples/hello-world; echo "exit $?"     # 1: replicas 3 -> 1, drift found
kubectl apply -k examples/hello-world                   # apply: the files win
```
