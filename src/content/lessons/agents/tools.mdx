A tool is a function you write, plus three things the model can read: a **name**, a **description**, and an **input schema** saying which arguments it takes. That's all the model ever sees of it. Here's one, in the shape Anthropic's API expects:

```json
{
  "name": "get_order",
  "description": "Look up an order by its order number: status, carrier and tracking link.",
  "input_schema": {
    "type": "object",
    "properties": { "order_number": { "type": "string" } },
    "required": ["order_number"]
  }
}
```

The docs put it plainly: the model "determines when to call a tool based on the user's request and the tool's description". The code behind it could look up an order, delete a database or order a pizza. The model only knows what the description says.

## The description is the interface

Anthropic's guide to building agents spends a whole appendix on this. It suggests writing a tool definition like "a great docstring for a junior developer on your team", with "example usage, edge cases, input format requirements". It also says to "poka-yoke your tools": shape the arguments so mistakes are hard to make.

A vague description doesn't produce an error. It produces a confident wrong choice. The widget below gives you a support agent with five tools. With `get_order` described as **"Gets data."**, try the normal question and see which tool the agent reaches for instead.

## Every tool result is an open door

Now the harder problem. The agent reads the support inbox, and whatever is in the email lands in its context, exactly like a tool result it asked for. If the email contains instructions, the model may follow them. OWASP calls this **indirect prompt injection**: it "occurs when an LLM accepts input from external sources, such as websites or files". It also says that "it is unclear if there are fool-proof methods of prevention for prompt injection".

That last sentence decides the design. If you can't reliably stop the model being fooled, you have to make being fooled survivable. OWASP's own list of mitigations comes down to two moves that don't depend on the model at all:

- **Least privilege.** "Restrict the model's access privileges to the minimum necessary for its intended operations." A support agent that answers order questions doesn't need a refund tool.
- **A person in front of risky actions.** "Implement human-in-the-loop controls for privileged operations." The model can *ask* to refund 37 orders. Someone has to say yes.

## What the widget showed

- **"Gets data." didn't fail. It misfired.** The closest-sounding description belonged to `issue_refund` ("Give an order number…"), so the agent refunded the order it was asked to look up. A precise description fixed it. So does giving a tool that moves money a description nobody could mistake for a lookup.
- **Read and write are different risks.** `read_inbox`, `get_order` and `search_help` can't hurt anyone. `send_reply` and `issue_refund` act on the world. OWASP's excessive-agency page has the same example: a mail assistant that only needs to read mail, but whose plugin "also contains functions for sending messages". Its fixes are a read-only plugin, a read-only access scope, and a person reviewing every email before it's sent.
- **The approval gate cost you a click per email.** That's the trade. The [business lesson](/learn/agents/business-agents/) puts numbers on it.

<Callout kind="real">
Real systems add more layers: tools that only accept specific order numbers, refund caps enforced in the payment code, separate credentials per tool, and logs of every call. They all share one property: none of them relies on the model choosing to behave.
</Callout>
