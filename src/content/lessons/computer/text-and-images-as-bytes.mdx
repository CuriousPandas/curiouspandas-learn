In 2017 a security researcher, Xudong Zheng, registered a web address that looked exactly like `apple.com` in the address bar of Chrome and Firefox. It wasn't. He explains a smaller version of the trick: "It may not be obvious at first glance, but "аpple.com" uses the Cyrillic "а" (U+0430) rather than the ASCII "a" (U+0061)."

Browsers already watched for a mix of alphabets. So he replaced every letter with a lookalike from one alphabet, and the protection "fails if every characters is replaced with a similar character from a single foreign language". He reported it to both, and it "was fixed in the Chrome trunk on March 24". Firefox was another matter. When he wrote, in April 2017: "The problem remains in Firefox as they decided that it is a problem for domain registrars to deal with." The trick works because of what a letter is to a computer:

They look the same to you, and they're different numbers to a computer. This lesson is about those numbers, and about what happens to them on the way to a disk or across a network.

## Characters are numbers

`ord` gives a character's number, and `chr` goes the other way. A table has to say which number means which character, and for that the world has settled on **Unicode**.

An earlier table called **ASCII** covered 128 characters: English letters, digits, punctuation and some control codes. It fit in 7 bits, and it's still the start of Unicode, so `A` is 65 in both.

Unicode's aim is to cover every writing system. Each entry is a **code point**, which the Python docs describe this way: "A code point value is an integer in the range 0 to 0x10FFFF (about 1.1 million values, the actual number assigned is less than that)." It's written `U+` and then hex, so `A` is U+0041. That's all Unicode is, in the first place: a very long, carefully argued list of numbers.

<Callout kind="trap" title="What looks like one character may not be">
Unicode has more than one way to write some things, so two strings that look identical can fail `==`. Run the lab below to see it.

And one "character" on screen can be several code points. A flag, or a family emoji, is a sequence of them joined together. So `len` tells you how many code points there are, not how many symbols a person would count. For comparing text properly, real Python has `unicodedata.normalize`, which needs `import`.
</Callout>

## From numbers to bytes

A code point can go up to 1,114,111, which doesn't fit in a byte. So how do you store a list of them as bytes? That's a separate decision, called an **encoding**. The obvious answer is four bytes per code point, but it would quadruple every ASCII file, and as the Python docs note, it isn't compatible with a lot of existing software.

The usual answer now is **UTF-8**, which the Python docs call "one of the most commonly used encodings". It uses as few bytes as each code point needs, from one to four. The table is short enough to read, and this is the whole of it, from the standard that defines it, RFC 3629:

| Code point | Bytes, where x is a bit of the code point |
|---|---|
| U+0000 to U+007F | `0xxxxxxx` |
| U+0080 to U+07FF | `110xxxxx 10xxxxxx` |
| U+0800 to U+FFFF | `1110xxxx 10xxxxxx 10xxxxxx` |
| U+10000 to U+10FFFF | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

Three useful things follow from that table. **ASCII text is unchanged,** so a file that was pure ASCII was already UTF-8. **The first byte says how many bytes this code point takes.** And **every following byte starts with `10`,** so a program that lands in the middle of a code point can find the next one.

Now try it. Type anything: other alphabets, or an emoji if your keyboard has them.

## When two programs disagree

The word for that garbage is **mojibake**, and you've seen it on real pages and emails: `CafÃ©`, where someone wrote `Café`.

Nothing was damaged. `é` is two bytes in UTF-8, `C3 A9`. An older encoding called **Windows-1252** gives nearly every byte one character, so it reads `C3` as `Ã` and `A9` as `©`. **The bytes were right, and the reading was wrong,** the same kind of mistake as on Ariane. There was no error, because in that table those bytes are perfectly valid.

Pure ASCII survives, since UTF-8 and Windows-1252 agree on the first 128 values. English isn't always pure ASCII, though: a curly apostrophe turns `don’t` into `donâ€™t`. So a program can pass all its tests on ASCII text, and then break on the first customer called José.

<Callout kind="trap" title="Whether the repair works">
You just repaired `CafÃ©` by turning it back into bytes with the wrong rule and reading them with the right one. It works until a byte has actually gone. Windows-1252 has five byte values with no character, and on those Python's `errors="replace"`, which this lab copies, writes the replacement character �, U+FFFD. That's what happened with `Á`. Now the original byte has been thrown away, and no repair can recover it. Not every program goes that way: a browser's version of Windows-1252 maps those five bytes to invisible control characters, and strict Python raises an error. But text that has been through a replacing step has values only the original data can fix.
</Callout>

Counts mislead here too. `len("😀")` is 1 in Python, while it's four bytes in UTF-8, and `.length` gives 2 in JavaScript, which counts in another encoding's units. ## A picture is a row of bytes

Text was numbers with an agreement on top, and a picture is too. A **pixel** can be stored as three bytes: how much red, how much green and how much blue, each from 0 to 255. So `FF 00 00` is pure red, and `FF FF FF` is white. Put pixels end to end, left to right and row after row, and you have a raw image.

Memory is one long row of bytes, and it has no rows or columns of its own. So the width is an agreement as well: to find the pixel at some row and column, you compute where it starts, `(row × width + column) × 3`.

That formula is worth a second look, because you've just met two of the most common ideas in how programs hold data. Each pixel is a **record**, a fixed set of fields at known positions: red first, then green, then blue. The picture is an **array**, a run of same-sized items, where finding one is a multiplication and an addition, however long the array is. That's why looking up an item in an array takes the same arithmetic for any position. [Arrays and lists](/learn/algorithms/arrays-and-lists/) goes further into what that layout buys you.

Raw pictures get big quickly. A 4K screen is 3840 × 2160 pixels, so at 3 bytes each one frame is 24,883,200 bytes, about 25 MB. Which is why most image files compress. PNG, for example, is described by its specification as a format for "lossless, portable, well-compressed storage of static and animated raster images", and it also stores the width and other settings at the start of the file, so the reader doesn't have to guess. Other formats, such as JPEG, save more space by discarding detail you're unlikely to notice. Sound and video are numbers in the same way, with their own agreements.

<GoDeeper title="Why JavaScript says 2, and what a surrogate is">
Some systems hold text in 16-bit units, and JavaScript's strings are one example. The encoding is **UTF-16**. A 16-bit unit reaches only as far as U+FFFF, so a code point above that becomes a pair of units from a reserved range, U+D800 to U+DFFF, called **surrogates**.

Those reserved numbers aren't characters, and they have no UTF-8 form. RFC 3629 forbids encoding them, and the Unicode FAQ says a UTF maps "every Unicode code point (except surrogate code points)". Real Python's `chr(0xD800).encode()` raises an error, and so does this page's model.

So `"😀".length` is 2 in JavaScript, because it counts UTF-16 units, and `len` is 1 in Python, because it counts code points. Both are right, about different things. This site's tests run both.
</GoDeeper>

## What to remember

- A character is a number from a table, and Unicode is that table. Two things that look the same may be different numbers.
- An encoding turns code points into bytes. UTF-8 takes one to four bytes per code point, and ASCII is unchanged in it.
- Garbled text usually means the bytes were right and the reading was wrong. Once a byte has been replaced, it's gone.
- Characters, code points and bytes are different counts. Know which one a limit is in.
- A picture is an array of records in one long row of bytes. Its width is an agreement, and so is everything else about it.
