In 2021 a player called t0st got tired of waiting for GTA Online to load, and went looking for the reason in a game whose source code nobody outside the company could read. On his old PC it took about six minutes, four of them with one CPU core flat out doing nothing else. (A core is one of the independent workers inside a processor, the CPU.) He found this: "It turns out GTA struggles to parse a 10MB JSON file". JSON is a common text format for data, and to parse a file is to read its text and turn it into data a program can use. The file held "some 63k item entries".

Two loops were eating the time, and neither looked like a loop in the code that called it.

**The first was inside a library call.** A library is code that comes with a language, ready to call. The parser read the file with its `sscanf` function, one small value at a time. Each `sscanf` first measured the length of all the text left, using another function, `strlen`, so a 10 MB file got measured again for every value in it. t0st was fair about this: "To be fair I had no idea most sscanf implementations called strlen so I can't blame the developer who wrote this."

**The second was a duplicate check.** Before storing each item, the game looked through every item stored so far. "It checks the entire array, one by one, comparing the hash of the item to see if it's in the list or not." (A hash is a number worked out from an item, which is quicker to compare than the item itself. [A later lesson](/learn/algorithms/hash-tables/) covers them.) And then the punchline: "And all of the items in the JSON are unique!"

His measurements, with a patch for each problem:

| Patched | Load time |
|---|---|
| Nothing | about 6 minutes |
| Duplicate check only | 4 min 30 s |
| JSON parser only | 2 min 50 s |
| Both | 1 min 50 s |

Those are one person's numbers on one old PC, and he reports around two minutes on high-end machines. Rockstar paid him a $10,000 bounty and shipped a fix. Its statement confirms he found "an aspect of the game code related to load times", and it doesn't say whether the fix was the same as his.

## Why nobody noticed

We can't see what Rockstar tested, but we can see why code like this survives. Both loops are fine on a small file. A catalogue of a hundred items loads instantly, so the code passes review, passes tests and ships. Then the data grows, a little at a time. Nothing ever breaks. It just gets slower.

Bruce Dawson has written up a run of these bugs in Windows, and he has the best description of them: "O(n^2) is the sweet spot of badly scaling algorithms: fast enough to make it into production, but slow enough to make things fall down once it gets there."

## Why a stopwatch alone isn't enough

A stopwatch tells you how long this code took, on this machine, with this input, today. Every part of that changes. What doesn't change is how the work grows when the input grows, and you get that by counting steps.

Take the duplicate check. The first item is compared with nothing, the second with one earlier item, the third with two. With `n` items, all different, that adds up to:

```text
0 + 1 + 2 + ... + (n - 1) = (n² - n) / 2
```

For 63,000 items, that's 1,984,468,500 comparisons. (t0st wrote `(n²+n)/2` and flagged it himself with "if my math is right". The difference is 0.003% and changes nothing, but the slip is a nice reminder that the shape matters more than the last digit.)

Now look at what happens when `n` doubles. `n²` becomes four times bigger, so the work quadruples. That's the signature of quadratic growth: **twice the input, four times the work**. You can read it off counted steps, with no stopwatch. Check it across a few doublings, because one pair of sizes can mislead. `2^n` also quadruples going from `n = 2` to `n = 4`. In the other direction, a quadratic program that does other work too can stay under 4x for a while: the slow merge sort in [a later lesson](/learn/algorithms/divide-and-conquer/) measures 2.92x, then 3.19x, then 3.44x.

<Callout kind="trap">
The dangerous line looked like the cheapest one in the program. `if x in seen` is a loop when `seen` is a list. So are `items.pop(0)` and `items.insert(0, x)`, because every item after that spot has to move. And so was `sscanf`, in a way its callers had no reason to expect. When a program gets slow as data grows, look for loops that don't look like loops.

## Names for the shapes

The shapes come up so often that they have names, written in a notation called **big-O**. `O(n²)` says "the work grows like n squared". The notation ignores fixed multipliers, because they change between machines and the shape doesn't.

To see why the shape matters more than the machine, here's the work at two sizes, with an invented, round speed of a million steps a second:

| Name | Big-O | 1,000 items | 1,000,000 items | Everyday example |
|---|---|---|---|---|
| Constant | `O(1)` | instant | instant | Look up one key in a dictionary |
| Logarithmic | `O(log n)` | instant | instant | Find a name in a sorted list by halving |
| Linear | `O(n)` | 1 ms | 1 second | Read everything once |
| n log n | `O(n log n)` | 10 ms | 20 seconds | A good sort |
| Quadratic | `O(n²)` | 1 second | 11.6 days | Compare each item with every other |

At 1,000 items, the worst row costs one second. That's the row that ships. A machine a thousand times faster only takes the bottom right cell from 11.6 days to about 17 minutes, which is why better algorithms beat better hardware once the data is big.

<Callout kind="real">
"Steps" in this lab aren't CPU instructions. It charges one for each statement, operation and call, plus whatever a single line hides, like a scan. Real instructions vary, and memory layout can change the real speed by a large factor, which is the next lesson's subject. A smaller big-O can even lose on small inputs. The shape tells you what happens as data grows, not which code is faster today, so measure too.
</Callout>

<GoDeeper title="What big-O formally means">
Big-O describes a set of functions. `O(f(n))` is every function `g(n)` for which there are constants `c > 0` and `n₀` such that `g(n) ≤ c·f(n)` for all `n ≥ n₀`.

So `(n² - n) / 2` is in `O(n²)`: take `c = 1` and `n₀ = 1`. The definition throws away the multiplier (that's `c`) and small inputs (that's `n₀`), which is exactly what makes it hold across machines. It's only an upper bound, so `n` is technically in `O(n²)` too. When people say "this is O(n²)", they nearly always mean that's the tight answer.

*Open Data Structures*, section 1.3, gives this definition and works through examples, and it's free.
</GoDeeper>

## What to remember

- Judge code by how its work grows, because that's what stays true on other machines.
- Twice the input and four times the work is the signature of quadratic. Check it across a few doublings, because one pair of sizes can mislead.
- Passing tests on small data tell you almost nothing about this.
- The slow line often doesn't look like a loop.
