On the morning of 31 December 2008, owners of Microsoft's Zune 30GB music player woke up to find it frozen. They couldn't play anything, and the device wouldn't finish starting. By that afternoon, more than 2,500 messages had piled up on Microsoft's support forum.

Microsoft's explanation that day was "a bug in the internal clock driver related to the way the device handles a leap year". Its advice was to let the battery run flat, wait until the next day, recharge the player and turn it on. That worked for most people, with no change to the firmware, the software built into the device. A few were still complaining the next morning.

The device hadn't misread its instructions. It was following them perfectly, and it would have gone on following them for as long as it had power. That's why a flat battery was the cure: starting again on a later date got through the loop normally. A post on Microsoft's developer blogs described what it was stuck on: "The problem is that when you're in the 366th day of a leap year, we don't go into the inner if so we don't subtract 366, and keep going into the while block forever."

You'll run that loop shortly. First, what do we mean by instructions?

## What makes it an algorithm

Jeff Erickson's textbook gives the definition we'll use:

> An algorithm is an explicit, precise, unambiguous, mechanically-executable sequence of elementary instructions, usually intended to accomplish a specific purpose.

A cooking recipe is the usual comparison, and it's a useful place to see the difference. "Bake until golden" needs a person who knows what golden looks like. "Add salt to taste" needs a tongue. "Heat at 200 degrees for 25 minutes" doesn't. Go through the words:

- **Explicit and precise.** Everything is stated, with nothing left to common sense.
- **Unambiguous.** There is one way to read each step.
- **Mechanically executable.** Following it takes no judgement at all.
- **Elementary instructions.** Each step is something the machine can already do. "Sort the list" isn't elementary until someone has told the machine how.

Notice what isn't on the list. This definition doesn't say the algorithm has to be right, or even that it has to finish. It says how clearly it has to be written down. Not every book agrees. Donald Knuth's definition, as Wikipedia quotes it (we haven't read the book), says "An algorithm must always terminate after a finite number of steps", and under that one the loop you're about to run isn't an algorithm at all. So check which definition a book is using.

## Watch a machine follow orders

Erickson's first example is a song: an algorithm for singing "Bottles of Beer on the Wall", for any starting number `n`. Here it is in Python. A program is the same steps, written in a language a machine can follow.

Press **Run** to see all of it. Then press **Step** to walk through one line at a time and watch `i` count down in the Variables panel. `for i in range(n, 0, -1)` means "let `i` be `n`, then one less, stopping before 0".

<CodeLab code={`n = 3
for i in range(n, 0, -1):
    print(i, "bottles of beer on the wall,", i, "bottles of beer,")
    print("Take one down, pass it around,", i - 1, "bottles of beer on the wall.")

Read the output closely. It says "1 bottles of beer". Anyone singing this would fix that without noticing. A machine can't, and that's the deal: you get perfect obedience, and you give up every correction a person would make without being asked.

## When the recipe leaves a decision open

Precise is harder than it sounds, because most of what we say leaves something out. Try two instructions that sound complete: "put these names in alphabetical order" and "round to the nearest whole number".

<CodeLab code={`print(sorted(["apple", "Banana", "cherry"]))
print(round(0.5), round(1.5), round(2.5), round(3.5))
`} />

"Banana" came before "apple", because Python compares the codes behind the letters, and every capital letter's code is lower than every small letter's. And `round(2.5)` is 2. Python's documentation says so: "if two multiples are equally close, rounding is done toward the even choice". Neither of these is a bug. Your instruction left a decision open, and someone you've never met closed it for you.

So an underspecified instruction doesn't make a machine stop and ask. It runs, and the gap gets filled by whatever its authors chose. If you want capitals ignored, or halves rounded up, you have to say so.

<Callout kind="trap">
Nothing warned you. Both lines ran without an error and printed something plausible. A program that does the wrong thing confidently is harder to catch than one that crashes, and that will come up again and again on this trail.
</Callout>

## The day the loop never ended

Here is the Zune code, translated into Python so you can run it. It works out the year from a count of days, where 1 January 1980 is day 1. Each pass of the `while` loop takes a whole year's days off the count and adds one to the year, until fewer than a year's worth of days remain. In `is_leap`, `%` gives the remainder after dividing, so `year % 4 == 0` asks whether the year divides exactly by 4.

Change the last line, and find out what happened on 31 December 2008.

<CodeLab mission="alg-what-last-day" />

When the count reached 366 in a leap year, the outer test said "more than 365 left, so go round again". The inner test said "not more than 366, so don't subtract". Nothing changed, so the next pass asked the same two questions and got the same two answers. Every instruction was clear, and every one of them ran.

It was also easy to miss. The loop hangs on one day in every 1,461, the last day of a leap year. On every other day it gives the right answer.

<Callout kind="real">
The page stops the loop at 5 million steps, because this lab counts them. The player had nothing like that, and neither would real Python: this loop would run until someone pulled the power. Here's what we can and can't check. Microsoft's public statement names the clock driver and the leap year, not this code. The code comes from a fan forum, as reproduced in that blog post, and we haven't seen the firmware. The post doesn't say how `days` is produced either. What we did check, with a test on this site, is that when 1 January 1980 counts as day 1, this exact loop hangs on the last day of a leap year and on no other day, which is the date Microsoft reported.
</Callout>

So an algorithm can be precise and still be wrong. Three separate questions are worth asking about any procedure:

1. **Can it be misread?** That's what the definition covers.
2. **Does it always finish?** On every input, not just the ones you tried.
3. **Is the answer right?** Also on every input.

Most of this trail is about a fourth question, which only makes sense once those three are answered: how much work does it take?

## What it does, and how it does it

A second distinction runs through the rest of this trail. Open Data Structures, a free textbook, puts it this way: "An interface describes what a data structure does, while an implementation describes how the data structure does it."

A **data structure** is a way of organising data so a program can use it. An **interface**, it goes on, "sometimes also called an abstract data type, defines the set of operations supported by a data structure and the semantics, or meaning, of those operations". You'll see it shortened to **ADT**.

Think of a phone book as a promise with two operations:

- `put(name, number)` stores a number under a name.
- `get(name)` gives back the number most recently stored under that name.

That's the interface. It doesn't say whether the numbers live in a list, on cards, or anywhere else. Here are two implementations. **A** keeps a list of pairs and looks through it. **B** uses a Python dictionary. Run it, and see whether both kept the promise.

<CodeLab code={`# Implementation A: a list of (name, number) pairs.
pairs = []

def put_a(name, number):
    pairs.append((name, number))

def get_a(name):
    for pair in pairs:
        if pair[0] == name:
            return pair[1]
    return None

# Implementation B: a dictionary.
book = {}

def put_b(name, number):
    book[name] = number

def get_b(name):
    return book.get(name)

put_a("Mei", 111)
put_b("Mei", 111)
print(get_a("Mei"), get_b("Mei"))

# Mei gets a new number.
put_a("Mei", 222)
put_b("Mei", 222)
print(get_a("Mei"), get_b("Mei"))
`} rows={18} />

They agree until Mei changes her number. Then A hands back the old one, with no error, because it finds the first match and stops. It looks like a phone book and it breaks the promise. A test that only ever stored each name once would have passed it.

To fix A, you could make `get_a` walk the list and keep the last match, or make `put_a` replace an existing pair. Try one. Both honour the interface, and they cost different amounts of work, which is the point of the separation: **the interface decides what's correct, and the implementation decides what it costs.** Later lessons take the common interfaces, list, stack, queue, set and map, and ask what each implementation charges.

<GoDeeper title="Proving a loop finishes">
To prove a loop ends, look for a **variant**: a whole number that can't go below zero and gets strictly smaller on every pass. A value like that can only shrink a finite number of times, so the loop has to stop.

In the Zune loop, `days` looks like a variant, since each pass subtracts 365 or 366. The proof fails on exactly one branch: a leap year with `days` equal to 366 changes nothing, so the number doesn't get smaller. Trying to write the proof points straight at the bug. Adding `else: break` closes that branch, and every pass then either shrinks `days` or ends the loop.

Whether a loop finishes can't be decided in general, by any program, for all programs. That's the halting problem. For one loop you can read, it's often this easy.
</GoDeeper>

## What to remember

- An algorithm is precise enough that following it takes no judgement.
- A machine gives you exact obedience and none of the corrections a person would make.
- Precise doesn't mean right. Ask separately whether it can be misread, whether it always finishes, and whether the answer is right.
- A gap in your instructions doesn't stop the machine. Somebody else's choice fills it.
- An interface says what a thing does. An implementation says how, and that's what sets the cost.
