Every change a PostgreSQL server makes is first written to its **write-ahead log** (WAL). That log is what makes the next two things possible.

- **A replica** (a standby) receives the primary's WAL and replays it, so it holds a live copy you can read from. It spreads read load and gives you a server to fail over to.
- **An archive** keeps every WAL file, alongside a periodic **base backup**. Together they let you rebuild the database as it was at any moment you choose. That's **point-in-time recovery** (PITR).

Both are copies, but only one of them is a backup.

## Lag you can see, and a mistake you can't undo by copying

<ReplicaLab mission="db-replica" />

## Reading your own writes

PostgreSQL's documentation says it plainly: WAL "takes some time to arrive from the primary server so there will be a measurable delay between primary and standby." Usually that's milliseconds, which is long enough for a user who saves a change and reloads instantly. The fixes trade cost in different places:

- **Route a user's reads to the primary briefly after they write.** Cheap, and everyone else still uses replicas.
- **Make the replica read wait** until it has replayed the write. The app remembers the write's WAL position and compares it with `pg_last_wal_replay_lsn()` on the replica.
- **Make commits wait** with `synchronous_commit = remote_apply` **and** the standby listed in `synchronous_standby_names` (without that, `remote_apply` quietly behaves like `on`), so the commit doesn't return until the standby has applied it. Every write pays for the round trip.

More replicas don't help. Each one lags just the same.

## Recovering a dropped table

Promoting the replica gives you a server with no `orders` table, because it already replayed the drop. Last night's backup brings back the table as it was at 02:00, without today's orders. Only the backup **plus the WAL archive**, replayed with `recovery_target_time` set before the mistake, brings everything back. By default (`recovery_target_inclusive = on`) PostgreSQL stops just after the target, so the target has to fall before the DROP and after the last order you want.

<Callout kind="trap">
A database with replicas looks protected, and a backup job that runs every night looks protected. Neither is, until you've restored it. The Resilience track's [Backups that actually restore](/learn/resilience/backups-that-restore/) covers testing restores. The short version: a backup you've never restored is a hope, not a backup.
</Callout>

<Callout kind="tip">
A **delayed replica** is a middle ground. With `recovery_min_apply_delay = 1h`, a standby stays an hour behind on purpose, which gives you an hour to stop it before it replays a mistake.
</Callout>

<DoItForReal id="db-rep-real" profile="gitops">

Look at what tilt's own database can and can't recover from:

```bash
kubectl -n cnpg-system get cluster demo-pg                 # INSTANCES 1: no replica to fail over to
kubectl -n cnpg-system get cluster demo-pg -o jsonpath='{.spec.backup}'; echo   # empty: no backup configured
```

The empty `backup` isn't an oversight. The Cluster's own comments in tilt say WAL archiving needs an object store, which a laptop doesn't have, and that a cluster with no backup stanza "looks configured and has no recovery path whatsoever". CloudNativePG's documentation agrees: "A valid WAL archive is required to perform PITR."

</DoItForReal>
