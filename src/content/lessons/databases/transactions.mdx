A **transaction** groups statements so they succeed or fail together. Move money between two accounts inside one, and you never see the money leave one account without arriving in the other. That's the promise most people know.

There's a quieter problem a transaction doesn't solve on its own: two people changing the same row at the same time.

## The lost update

The shop has 10 panda tees. Two clerks each sell one, half a second apart. Each clerk's app does the obvious thing: read the stock, subtract one, and write the result back.

## Why the transaction alone didn't help

PostgreSQL's default isolation level is **Read Committed**: each statement sees the data committed before it began. Clerk B's `UPDATE` found the row locked by A, so it **waited for A to commit**, exactly as the documentation describes. Then it carried on and wrote its 9. The database protected the row. It couldn't know that B's 9 was based on a number that was no longer true.

The three fixes all stop B from acting on a stale read:

| Fix | What changes | Cost |
|---|---|---|
| `SELECT ... FOR UPDATE` | B's *read* waits until A commits, so B reads 9 | Clerks queue for the row |
| `SET stock = stock - 1` | The database does the arithmetic on the current value; no stale read exists | Only works when the change is a simple calculation |
| `REPEATABLE READ` | B's write is refused with a serialization error | The app must catch the error and retry |

<Callout kind="trap">
At `REPEATABLE READ` or `SERIALIZABLE`, PostgreSQL's documentation is direct: applications "must be prepared to retry transactions that fail due to serialization errors". An app that shows the error to the customer, or quietly swallows it, has swapped a lost sale for a refused one.
</Callout>

<Callout kind="real">
The same bug turns up as double-booked seats, overdrawn balances and reused coupon codes, anywhere code reads a value, decides, and writes back. The pattern to look for in code review is a `SELECT` followed by an `UPDATE` that writes a number the application calculated.
</Callout>

<DoItForReal id="db-tx-real" profile="gitops">

The `gitops` profile runs a CloudNativePG cluster called `demo-pg`. Open **two terminals** and connect both:

```bash
kubectl -n cnpg-system exec -it demo-pg-1 -- psql demo
```

Then, in each terminal in turn (A first, then B, then back to A):

```sql
CREATE TABLE IF NOT EXISTS items (sku text PRIMARY KEY, stock int);
INSERT INTO items VALUES ('panda-tee', 10) ON CONFLICT (sku) DO UPDATE SET stock = 10;  -- terminal A only
BEGIN;
SELECT stock FROM items WHERE sku = 'panda-tee';           -- A, then B: both see 10
UPDATE items SET stock = 9 WHERE sku = 'panda-tee';        -- A, then B: B hangs
COMMIT;                                                    -- in A: watch B's UPDATE finish
COMMIT;                                                    -- in B
SELECT stock FROM items WHERE sku = 'panda-tee';           -- 9
```

Repeat with `SELECT ... FOR UPDATE`, and then with `BEGIN ISOLATION LEVEL REPEATABLE READ;`, and compare.
