It's late, the payment test won't pass, and the quickest way to try the real API is to paste the key into `config.env`. It works. Everything gets committed together. Ten minutes later someone spots the key, deletes the line, and commits again. "Fixed."

It isn't. Remember what a commit is: [a snapshot of every file](/learn/git/what-is-git/), named by the hash of its contents. The fix made a *new* snapshot without the key. It didn't touch the old one, and it can't: change a commit and its name changes, along with [every name after it](/learn/git/inside-git/).

## Leak it, delete it, read it back

The key below is fake, and shaped so that no real scanner will mistake it for a real one. That's the only difference from the real thing.

<GitPlayground mission="git-secret-history" title="The Friday fix" />

`git show <commit>:<file>` prints a file as it was in any commit. `HEAD~1` means "one commit before HEAD". Anyone with a copy of the repository can do this, for every commit ever made.

<Callout kind="trap" title="The fix that only looks like a fix">
Deleting the line, deleting the file, even making the repository private: all of these change what you see *now*. None of them changes what already left. The key has been readable from the moment it was pushed.
</Callout>

## The one fix that works

If a secret was pushed, **treat it as stolen**. Go to whoever issued it, revoke it, and issue a new one. A revoked key is worthless wherever it ended up. GitHub's own guide puts this first, and notes that once the secret is revoked or rotated, that "may be sufficient to solve your problem."

You *can* rewrite history to take the old commit out (tools like `git filter-repo` do this). But GitHub's guide is plain about what that cannot reach: other people's clones, forks that contain the commit, cached views of the commit by its hash, and pull requests that reference it. Rewriting tidies your copy. Rotating protects you.

## Stop it before it leaves

The cheapest leak is the one that never gets pushed:

- **Keep secrets out of the working tree.** Read them from the environment or a secrets manager. List local config files like `.env` in `.gitignore` so `git add .` can't sweep them up.
- **Scan before you push.** [gitleaks](https://github.com/gitleaks/gitleaks) checks a repository's whole history for known secret formats, and can run as a pre-commit hook and in CI.
- **Let the server refuse.** GitHub's push protection blocks a push that contains a secret in a format it recognises, before it reaches the repository. For your own account it's on by default when you push to public repositories.

<Callout kind="real">
Scanners recognise secrets by shape: the prefixes and lengths real providers use, plus high-entropy strings next to words like "key". That's why the key in this lesson is shaped like nothing real - a lesson shouldn't trip alarms. It's also the limit of scanning: a secret in a shape nobody taught the scanner can still get through. Scanning is the seatbelt. Keeping secrets out of the repository is the driving.
</Callout>

<DoItForReal id="sec-secrets-real">

Find out whether a string ever entered a repository's history. `-S` lists the commits that added or removed it, and `-p` shows the change:

```bash
git log -p -S "PAYMENT_KEY" --all
```

Then scan a repository of your own with [gitleaks](https://github.com/gitleaks/gitleaks#installing):

```bash
gitleaks git -v .
```

`gitleaks git` reads the history, not just today's files. (Older guides say `gitleaks detect`; it still works but was deprecated in v8.19.)

</DoItForReal>
